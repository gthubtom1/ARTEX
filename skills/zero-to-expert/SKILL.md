## name: zero-to-expert
description: 把"专家级渗透判断"固化成可执行纪律：路线选择顺序、证据门、复现门、常见卡点处置、以及每次交付的人话教学输出。当任务目标是靶场/授权资产，且使用者的安全经验有限、需要工具替他做专业判断时使用。

# 零基础 → 专家替身

本技能不教工具用法，只做一件事：**把专家在环的那个"人"，拆成可执行的规则**，让 agent 自己按专家顺序做决定，并把过程翻译成人话回报。

核心前提：**判断力不能靠模型自觉，必须变成硬门。** 任何"我觉得验证过了"都不算，必须过下面的证据门与复现门。

---

## 一、路线选择顺序（侦察阶段唯一允许的默认序）

按成本从低到高，**不许跳级**。前一步没有明确产出就不进下一步：

1. **被动面**：指纹（server/框架/CMS/语言）、标题、证书 SAN、robots/sitemap、`.git/.env/backup` 等常见泄露、公开 JS 里的接口与硬编码密钥。
2. **目录/文件面**：只跑小字典（≤ 5000 条，`-t 20`），命中即停，不做全量爆破。
3. **认证面**：登录框、注册、找回密码、JWT/Cookie 结构、默认口令（admin/admin、admin/password 各试一次，不爆破）。
4. **参数面**：已发现的 endpoint 逐个看参数语义（id/url/file/path/cmd/redirect/template），先做**无害探针**（加单引号、加 `[]`、改类型、加 `../`、换 URL 主机），看响应差异。
5. **已知漏洞面**：只有拿到了准确版本号才去比对 CVE；**比对结果只是线索，不是漏洞**。
6. **深度利用**：仅在 1–5 有实证时进入，按"上一步的真实产出"决定下一步，不预设链条。

> 靶场（HTB/VulnHub/DVWA/Juice Shop）额外优先：web 目录 → 上传点 → 反序列化/模板注入 → 数据库/文件读取 → 拿 shell → 本地提权（先 `sudo -l`、SUID、cron、可写服务，再考虑内核）。

## 二、证据门（写 finding 前的硬检查）

调用 `report_finding` 之前，逐条自问，**任一条答不上就不许报**：

1. **我本轮真的发出过这个请求/命令吗？**（不是"根据版本推断"，不是"参数看起来可以"）
2. **响应里有没有能证明"越权/执行/泄露"的原文？**（状态码变化不算，要有数据差异、回显、文件内容、命令输出）
3. **这个证据能不能贴出来给别人照着重放？**（完整 URL + 方法 + 关键 payload/参数 + 关键响应片段）
4. **换一条独立路径能再触发一次吗？**（换个 id、换个参数位置、换个编码；只能复现一次的，标 inferred）

四条全过 → `report_finding`，`confidence=observed`。
第 4 条没过 → `record_fact` + `confidence=inferred`，summary 写明"已验证存在、复现稳定性未知"。
一条都没过 → 不写，继续探。

## 三、复现门（自检的标准动作）

对每个候选发现，做**一次与首次不同的复现**，二选一：

- **同漏洞不同载体**：SQLi 用布尔差异证过，就用时间盲注再证一次；XSS 用弹窗证过，就用 `document.domain` 读取再证一次。
- **同漏洞不同入口**：同一参数换个 HTTP 方法、换个 Content-Type、换个路径写法（`/a/../b`、大小写、分号参数）再触发。

复现失败时**不许**把首次结果升级为 confirmed，也不许重试到成功为止（那是把噪声当信号）。正确动作：记 inferred + 写明失败的那次怎么失败的。

## 四、常见卡点 → 专家处置（照做，不要自由发挥）

| 现象 | 新手会做错的事 | 专家动作 |
|---|---|---|
| 注入无回显 | 反复换 payload 硬试 | 转时间盲注/带外（DNS 回连），或换参数位置；两次无差异即记为不可注入 |
| 上传被拦 | 只改后缀 | 依次试：Content-Type、图片马 + 解析路径、`.htaccess`/`.user.ini`、分片、双扩展名、大小写 |
| 拿到 403/WAF 页 | 认为"目标有防护，放弃" | 先判断是**目标防护**还是**平台拦截**；平台拦截（带"ARTEX 平台管控"字样）必须换路线，不许改写绕过 |
| 拿到 shell 但命令无输出 | 反复重连 | 确认是否反弹到内网不可达、是否 PTY 问题、是否被 egress 代理改写；改用带外通道或文件落地 |
| 版本匹配到 CVE | 直接报漏洞 | 只记为线索，去实际触发一次；触发不了写 inferred |
| 扫描器报了高危 | 直接采信 | 扫描器只提供候选，**必须手工复现**才进报告 |
| 一处打不动 | 死磕两小时 | 换本质不同的攻击面（另一个入口/另一类资产），保持 2–3 条路线并行 |

## 五、教学输出（每次交付必须带，这是"零基础也能用"的关键）

任务收尾时，除了漏洞报告，额外输出一段固定结构的人话说明，**不许用术语糊过去**：

```
■ 我做了什么（按顺序）
  1) <动作> → <拿到什么>
  2) ...
■ 确认的漏洞（每条一段）
  - 是什么：<一句话，不用行话>
  - 在哪：<完整地址/参数>
  - 怎么证实的：<那次请求和响应里最关键的一行>
  - 能造成什么后果：<数据/权限/影响面>
  - 怎么修：<一句可执行的话>
■ 没打通的（及原因）
  - <方向>：<卡在哪一步，是目标防护还是我们缺工具/缺权限>
■ 下一步建议（3 条以内，按性价比排序）
■ 本次踩的坑（给使用者积累经验用）
  - <坑> → <下次怎么避免>
```

**纪律**：这段只能写真实发生的事。没验证的不进「确认的漏洞」；不确定的写在「没打通的」里并标原因。宁可少写一条，不许编一条。

## 六、范围红线（凌驾于以上一切）

- 只操作任务目标里明确列出的主机/域名/IP 段。**发现范围外的新资产不等于获得授权**，记一条 out-of-scope 的 fact 并跳过。
- 不做破坏性操作：不删库、不改配置、不留后门、不做持久化、不横向到范围外、不碰生产写操作。
- 遇到凭据/密钥：记录下来供报告使用，**不写入日志外发、不用于范围外系统**。
- 平台拦截（消息里带「ARTEX 平台管控·非目标防御」）= 策略决定，**换路线**，不要试图改写命令绕过。
