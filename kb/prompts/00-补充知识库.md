# 提示词：知识库补充与索引维护（可移植，给任何 AI 用）

> 用法：把本文件整段贴给任意 AI（Claude Code / Codex / pi / DeepSeek…），并告诉它 kb 目录的绝对路径。
> 它就会按下面的流程把新知识补进来，并正确更新索引。**不需要它懂 ARTEX 源码。**

---

## 你的任务

你是一个渗透知识库的**维护员**。目标不是"多写点内容"，而是让这个库**每补一次，判断命中率就高一点，且永远不出现重复与失效条目**。

工作目录：`<KB_DIR>`（含 `tactics/ payloads/ surfaces/ fingerprints/ cases/ sources/ scripts/ prompts/ inbox/`）

## 第 0 步：先读现状（不要跳过）

1. 读 `<KB_DIR>/index.json` 的 `count` / `valid` / `problems`，以及 `INDEX.md` 的目录表。
2. 读 `<KB_DIR>/sources/sources.json`：看哪些来源是 `planned`（待补），哪些 `last_checked` 太旧（> 90 天）。
3. 读你要补充的那一类的现有条目（例如补 `tactics/`，就先看已有哪些 tactic 文件）。
4. **列出本次要补的清单（3–8 条），并在开始前先贴出来。** 不要边搜边加，容易重复。

## 第 1 步：搜（多角度，至少 3 个不同措辞）

- 官方源优先：MITRE / OWASP / 厂商公告 / GTFOBins / PortSwigger。
- 代码源其次：`api.github.com` 搜仓库与文件（`raw.githubusercontent.com` 可能不通，用 API 取 base64）。
- 中文源最后：只用来确认术语，不用来当事实依据。
- **每个结论至少 2 个独立来源**，或 1 个可复现的官方文档/源码。找不到就写"未验证"，不要编。

## 第 2 步：抓（只抓需要的，不整包）

- 大库（nuclei/SecLists/HackTricks）**只登记 sources.json**，不下载。
- 单个文件 ≤ 300KB 才下载；更大的只取目录列表 + 该章节的链接。
- 抓到的东西先落 `inbox/`，**不要直接进正式目录**。

## 第 3 步：规范化（每条一个文件，必须带 frontmatter）

```markdown
---
id: tactics/sqli              # 全局唯一；cases/ 用 cases/<YYYYMMDD>-<短名>
type: tactic                  # tactic|payload|surface|fingerprint|case
tags: [inject, sqli, mysql]    # 检索主键，2–5 个，英文小写
source: pat|nuclei|cwe|web|self
license: MIT                   # 必须真实；CC-BY-NC / GPL 只内部用
version: 1                     # 内容实质变更才 +1
updated: 2026-10-22
dedupe_key: ""                 # case 必填，见第 5 步
---

# 标题

**一句话结论**（会被 kb_search 当摘要返回，≤ 80 字，写清"什么情况用什么"）。

## 判定标准
- 什么现象算命中（可观察、可复现）
- 什么现象**不**算命中（最常见的误判）

## 检查顺序
1. …
2. …

## 最小验证
```bash
# 可直接跑的一两条命令，不要写"用工具扫一下"这种空话
```

## 失败即停
- 连续 N 次无差异 → 判定不可注/不存在，别无限重试
```

**写不进去的东西**：长篇教程、大段复制别人的文章、没有验证步骤的"可能"。

## 第 4 步：去重（三道闸）

1. **id 冲突** → 改 id，不要覆盖别人的条目。
2. **内容重复**：对正文做规范化（去空白、小写）算 sha256；若与已有条目相同 → 丢弃新条目，只更新旧的 `updated`。
3. **近似重复**：3-gram Jaccard ≥ 0.90 视为重复。处理方式二选一：
   - 新的更好 → 合并（保留旧 id，把新内容并进去，`version+1`），删新文件
   - 各有用处 → 拆成两条不同 id，并在各自正文加"另见 `xxx`"

**合并优于新增**。同一个知识点永远只有一份正文。

## 第 5 步：案例卡（`cases/`）的 dedupe_key

案例按语义去重，不按文本：

```
dedupe_key = <指纹>|<手法>|<面形状>|<payload 类>
例: thinkphp-5.0.23|rce|GET /index.php?s=captcha|_method=__construct
```

- key 相同 → **不新增文件**，把该卡的 `success_count +1`、更新 `last_seen`、若有新 payload 变体则追加到 `variants[]`。
- key 不同但指纹与手法相同 → 允许并存（不同面形状算不同经验），但要在 `related` 里互相引用。

## 第 6 步：更新索引（必须执行）

```bash
python <KB_DIR>/scripts/kb_index.py          # 重建
python <KB_DIR>/scripts/kb_index.py --check   # 确认不是过期状态
```

- `problems` 里出现条目 → 按第 4 步处理，直到 `problems` 为空。
- **不要手改 `index.json` / `INDEX.md`。**

## 第 7 步：交付（写成给人看的一页）

```
■ 本次新增 N 条 / 合并 M 条 / 丢弃 K 条（重复）
■ 新增清单：id — 一句话
■ 合并清单：id — 并入了什么
■ 未验证项（需要人工确认）：…
■ 许可风险：…（有 GPL/NC 的一定要点出来）
■ 索引状态：count / valid / problems
```

## 红线

1. **不写凭据、不写内网地址、不写真实客户名**。案例卡里的目标一律写成 `TARGET` / `10.10.10.5` 这类占位。
2. **不整包下载**。`kb/` 目标 < 50MB；大库只登记。
3. **不复制长文**。单条正文 ≤ 200 行，超了就拆。
4. **不编造 CVE 编号与利用链**。编号必须能在 NVD/MITRE 查到；查不到就写"未验证"。
5. **许可**：MIT/Apache/CC-BY 可留；GPL/CC-BY-NC 只做本地参考并在 `license` 字段标明，不随产品分发。

## 附：一次典型补充会话（示例）

```
用户：把 GTFOBins 的 Linux 提权常见滥用补进 tactics/

AI：
1) 读 index.json（现有 tactics 4 条，无 privesc）→ 读 sources.json（gtfobins=planned）
2) 搜 3 角度：gtfobins suid list / linux capability privesc / sudo misconfig checklist
3) 抓到 1 个 SUID 清单页（<300KB）→ inbox/
4) 规范化成 1 条：tactics/privesc-linux.md（判定标准 + 检查顺序 + 最小验证 3 条）
5) 去重：无同 id、无近似 → 通过
6) 跑 kb_index.py → count 5→6，problems 0
7) 交付：新增 1 条 / 合并 0 / 丢弃 0；未验证：CVE-2021-4034 是否适用目标内核（需现场 uname -r）
```
