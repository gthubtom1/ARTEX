## 四、未发现断链的项目

- 32 个侧边栏 URL **全部**有对应页面；
- 240 条路由**无重复注册**；
- `p2api` 12 条路径**全部**能匹配到路由（含 `{id}` 动态段）；
- 新页面裸 `fetch` 全部指向真实路由；
- 63 个工具名在**同一 agent 内无重复**；跨 agent 重叠是有意的（如 `list_findings`）；
- 新增表（capabilities/assets_owned/access_refs/routes/asset_checks/creds_vault/evidence_timeline/audit_log 等）均由 `0001–0003` 迁移创建，实机读写通过；
- 新增设置键（inject/asset/net）均有默认值或显式 fallback。

## 四点五、为什么精简 Planner（不是背离原版）

- 原版 `PlannerTools` 只有 10 个工具引用、`WorkerTools` 5 个（其余是 SDK 默认工具）；原版纪律就是**规划者只规划、执行者只执行**。
- 我们新增的能力卡/台账/凭据/立足点等读取工具，最初把 Planner 堆到 36 个（含 nmap/httpx/nuclei、data_locate、cred_harvest、session_exec、cred_reuse_run 等执行类），既偏离原版职责，也挤占规划轮上下文。
- 现在 Planner 28 个：保留原版读态势工具 + 新读工具（rank_intents/diagnose_progress/list_capabilities/cred_list/session_list/owned_list/owned_due/route_resolve）；扫描与执行全部只在 worker/main。这是**回到原版分工**，不是减少能力。

## 四点六、retester ↔ verifier 已合流（本轮新增）

- retester：把 finding 的 PoC 重放一次，产出 `reproduced|fixed|inconclusive`（原项目已有）。
- verifier：独立模型判断证据是否支持结论（二开新增）。
- 现在 `server/verifier.go` 在复核前查询该 finding 最近一次 `completed` 复测，把 verdict/摘要喂给复核提示词；规则：`reproduced` 可作为独立复现的强证据，`fixed/inconclusive` 不得判 verified。两条线不再是各说各话。

## 四点七、"写操作回放"为什么不做

- 原版 ARTEX **没有回放功能**；我们的 `internal/replay` 是新增的**只读回放**（curl GET/nmap -sT/-sV/nc -z/dig/whois）。
- 写操作（POST/上传/删除）回放等于再打一遍目标，必须先把目标复制成"影子环境"（副本/快照）才安全；当前没有影子环境，所以明确不做，避免误伤真实目标。只读回放已覆盖"复现 finding / 目标变更对比"的大部分场景。

## 四点八、并行测试死锁

- 原因：多个包并行共用同一个 PostgreSQL，偶发 40P01 死锁（测试基础设施问题，不是产品运行问题）。
- 处理：`scripts/accept_all.sh` 的测试改为 `-p 1`（串行），CI 同样建议串行；功能无影响，稳定性优先。

## 五、残留风险（不影响当前交付）

1. Worker 仍有 41 个工具（执行面全开）；若实际使用中模型出现"选错工具"，可再按任务类型裁剪。
2. 并行 `go test ./...` 偶发 PG 40P01 死锁 flake；建议 CI 用 `-p 1`（已写入台账）。
3. 任务达成时的"能力卡自动派生"未启用（后端改动按约束回退）；依赖 `progressHook` 期间或 agent 显式 `record_capability`。
4. 写操作真回放、retester→verifier 合流仍待做。
