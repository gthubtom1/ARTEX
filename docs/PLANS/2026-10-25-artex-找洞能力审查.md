> "我们要找到漏洞啊。让它审查一下我们当前这个项目能不能**快速地找到各个漏洞**，然后判断这些漏洞有没有什么用。

| **S5 上报** | 三门闸 | ✅ **不堵（默认档）** | `infer` 档下：空证据 → 仍入库、只降到 `inferred`（`agent/finding_gate.go:62-74`）；`rejected` → 改写成 fact（`internal/findinggate/findinggate.go:102-103`）——**洞不丢、线索也不丢**。所以 S5 不是卡点；真正的伤害在 S6：**入库了但等级不涨**，此时界面上看到的仍然是"还只有侦察信息" |

### 2.2 它找洞的"方法论"在哪？缺哪一层？

**现状是三层，全部是自然语言，没有一层可机检**：

1. **模板 goal 散文**（唯一"有序打法"）——`db/seed_templates.go`：① 在 `:24-43`、③ 在 `:62-84`、①③⑤ 的三段式重写在 `primaryTemplateOverrides :184-235`。

### 2.4 审查官／阶段门／闸门：在帮它找洞，还是在挡它？

**各给一条实例（帮 1 条、挡 3 条）。**

**✅ 帮上的一条：`report_finding` 落库当场唤醒 planner。**
`agent/worker.go` 里 `tsx.SetNotifyFinding(notifyFinding)` → engine 的 trigger 队列 → planner 立刻带"哪个意图发现了什么"重规划（`agent/planner.go:186-215` `renderTriggers`）。
这件事在 #19 上的效果可观察：3.5 分钟里完成"注入绕过 → 拿会话 → 读 1 条交易记录 → E4"（`docs/26:205-215`），没等 worker 跑完 1200s 的预算。**这是全仓最有效的"找洞加速器"**，它值得被复制到"没找到"的场景（见 P1-02）。

**⛔ 挡路的三条：**

1. **阶段门把最会出洞的工具锁在"你得先有洞"之后。**
   `reconForbidden` 含 `sqlmap`（`guard/guard.go:66-73`）；放行靠 `conclusive`（`server/server.go:4808`）。
   更细一层：`conclusive` 数的是 `assumptions` 表，而这张表有**两个不同语义的写入方**——"否定结论"（`db/hooks.go:39-66` `NoteAssumptionIfNegative`）和"侦察未使用结构化工具"（`db/hooks.go:145-172` `AssertReconUsedTool`）。→ 文档说的"已出结论"实际是"否定结论 + 侦察告警"混算，**放行条件与口径不一致**。
   用户视角：选了"① 值不值得打（20 分钟）"这个**推荐起步模板**，然后在一个有 SQLi 的站上被禁止用 sqlmap。

2. **授权门把"读数据"变成"等人"。**
   `data_dump` 类拦 `sqlmap --dump/--sql-shell`、`mysqldump/pg_dump/mongoexport/redis-cli --rdb`（`guard/guard.go:112-115`）；拦下后靠 `OnGrantNeeded` 找人（`guard/guard.go:82-87`）。
   #19 的 blockers 里确实出现了 `policy_blocked`（`docs/26:216` 一页纸的"还差什么"、`:235` 回归里的 blockers）——**它靠"人恰好在看"才走通**。这不是稳定的找洞路径。

3. **审查官在最需要"换打法"的时候只能写散文。**
   动作白名单只有 5 种：`kill_intent / retry_intent / set_next_stage / propose_intent / ask_human`（`internal/review/gate.go:137-205`），且：
   - `retry_intent` 只允许 `LastError ∈ {self_error, env_error}`（`gate.go:175-180`）→ **"目标侧没反应/打空了"不允许重试**；
   - `kill_intent` 要求 `target_blocked` **且已试≥3 次**（`gate.go:181-189`）；
   - `propose_intent` 永远 `NeedHuman=true`，**连 auto 档也不自动执行**（`gate.go:338-371` `NeedHumanFor` / `isAutoSafe`）→ 它提的"新方向"只会变成一条 hint（`server/review.go:580-590`）。
   真机结果：`docs/21-效果验收.md:21` —— **"审查官结构化动作 0｜一直 actions=[]（只写正文）"**。两次真跑都如此，不是偶发。
   而且它的**触发条件全是"停顿"**：`NoProgressRounds≥3 / 某意图 attempts≥5 / 预算过半且 stuck / stuck≥2`（`server/review_loop.go:326-339`）——**没有一条是"已经出洞但没换成收益"**。

### 2.5 #18 vs #19 差在哪里（归因到机制，不归到"目标写得好"）

先固定可核对的差异（`docs/26` §九、§12.2）：

| | #18 | #19 |
|---|---|---|
| goal 文本来源 | 模板（"只读、每类 ≤3 条样本、不改数据、不落文件"） | 人手写（"用 /doLogin 的 uid 注入绕过认证拿后台会话，再读 1 个账户交易记录（≤3 条）"） |
| 继承来源 | `source_task_ids=["14"]`（#14 已 E4） | 无 |
| 输入 token | 3,170k | 354k |
| 输出 token | 85k | 9.7k |
| 结果 | 0 finding / E0 | 1 critical / E4 |

**归因（按证据强度排序，前 3 条有代码指针，第 4 条是推断）**：

1. **【强】继承让每一轮都多付一份"别人的历史"。**
   `graphOverviewData` 把 `related_tasks` 拼进态势（`agent/tools.go:537`），每轮 planner 都重算、每段 worker 也拿（`agent/worker.go` `renderWorkerGraphOverview`）。上限是**每个来源任务 8,000 字正文 + 12 facts + 6 findings + 8 条 recent_done（每条 800 字 result_summary）+ 6 个 cold digest + 12 条 scope**（`agent/tools.go:631-638`）。
   #18 的 planner 提示词里能读到 #14 的 goal/description（各 800 字，`:750-751`）。**这是 8.96× 输入差里唯一有确定出处的部分**；它是"每轮重复支付"，所以随轮数线性放大。
2. **【强】#19 的首刀是一句"可执行的动作"，#18 的首刀是一句"要求"。**
   planner 的全部打法输入是 `{{.Goal}}`（2.2）。#19 的 goal 自带**入口(/doLogin)+手法(uid 注入)+停止条件(读 1 条、≤3 条)**→ 第一次 `add_intent` 就能写成一条 worker 一轮跑完的意图。#18 的 goal 是"每类 ≤3 条样本"这种**验收口径**，入口与手法要 planner 自己从继承的 facts 里重新拼→ 必然多轮：定库类型 → 查 information_schema → 取样本，**每一步之间都要等 worker 跑完再唤醒 planner**（S3 单刀串行）。这解释了 #18 输出 token 是 #19 的 8.79×（做得多）却 0 洞（每步都没闭合）。
3. **【强】#18 正好撞上三个"减法"机制。**
   - `ShouldFreeze(attempts≥4 && yields==0)` → `add_intent` **代码层拒绝**再派同向（`agent/tools.go:1136-1139` ← `internal/gatechain/gatechain.go:349`）；而 `yields` 只数 **fact**，不数 finding（`agent/tools.go:2236`）→ 一个"报了洞但没写 fact"的方向会被判 0 产出并冻结。
   - `frozenAssets`：决策队列判过"换目标"的资产不再派单（`agent/tools.go:1141-1148`）。
   - 意图去重靠 summary **文本相似度 ≥0.72**（`internal/gatechain/gatechain.go:337-346`）→ "查 information_schema" 与 "查 users 表" 很容易判成同向。
   → 结果：**"换个说法再试"被系统性禁止**，而 #18 需要的恰恰是"换一层再试"。
4. **【推断】** 每意图墙钟 1200s（`db/db.go:234` `COALESCE($6, 1200)`）≥ 模板①的总预算 1200s（`db/seed_templates.go:27`）→ 一条意图可以吃掉整个任务窗口，且 planner 心跳下限 600s（`server/engine.go:816-825`）。7.5 分钟里如果首刀 worker 一直在跑、又没交出 fact，planner 只能等边沿或心跳——而"连续无新事实"恰好是审查官的触发条件（2.4），**它这时候只会写一段散文，不会换一把刀**。

> **所以"目标写得好"只是表层。真正的机制是**：目标写法通过"S2 是唯一方法论入口"放大；继承让每轮更贵；三个减法机制禁止重试同向；而没有任何一个机制负责"第一刀砍空 → 换一把"。

### 2.6 "漏洞有没有用"这层判定，能不能反过来指导打哪里？

**能，而且零件已经写好了，只是被设计成只读、不给 planner 看。**

- `server/goal_fit.go` 的纪律注释原文：**"只读。它只是把已有证据翻译成「你的目标能到什么程度」，不派活、不改状态。"**（`server/goal_fit.go:21`）
- `goalDef.Need` 就是"这个目标需要哪几个能力"的结构化清单（`db/data/admin/rce/filewrite`，`server/goal_fit.go:32-90`）——**这正是"事前往哪打"的选择依据**。
- `buildNextMoves` 已经产出 **Top3 + 每条的成本/成功长相/失败怎么办**（`server/goal_fit.go:402-446`），完全符合"事前选点"需要的形态。
- `applyApplicability` 已经能判"**这个站看起来有没有这类面**"（`server/goal_fit.go:356-400`，`likely/unknown/unlikely`）；工作区并行改动（产品审查 P0-07）还给它加了"已确认漏洞里有通向该能力的类型 → likely"的兜底。
- 但它唯一的消费者是 `/brief` 与 `/fit`（`server/brief.go:177`、`server/goal_fit.go:264-274`）。**planner 的 `graphOverviewData` 里没有 `next_moves` 字段**（`agent/tools.go:373-600` 全字段可核对）。

**结论**：今天它是**事后判定**；把它变成**事前选点**只需要"把 `next_moves` + `applicable` 作为只读块塞进 planner 的态势"，不需要新算法（任务 **P1-03**）。

**但有一个真实约束必须先说清（否则这条会变成新的说谎源）**：
`fit` 的状态（yes/one_step/no）来自战果行 `done`（`server/goal_fit.go:123-175`），而战果行 `done` 来自 finding/证据 → **在 0 finding 时所有目标都是 `no`**，此时 `next_moves` 是空转的。
所以事前选点必须用 **`applicable`（站点面）+ 模板里"看到什么算有"** 驱动，**不能**用 `Need` 满足度驱动。这条写进 P1-03 的验收里。

## 六、FINALIZE：Know-but-not-done（故意不做 / 暂缓，附理由）

| 不做的 | 理由 |

| **把审查官改成能直接 `add_intent`** | 与 ADR（`docs/00 §3` 不可返工决定）里"审查官只读、不动证据/不派活"冲突。要么走 `P1-02` 的白名单动作（保留可审计 + 可撤销），要么先改 ADR。**改 ADR 需要用户拍板**，不在本文件范围。 |

## 七、三个最大风险（各一句）

1. **`P0-05` 不做就永远无法说"变快了"**——今天 `bench/results/` 只有一个 README，`first_finding_ms` 一次都没产出过；在这之前所有"优化了找洞"的说法都是不可反驳的，等于把 `docs/21` §一那种"60M token / 2 洞"的账继续记下去。
2. **`P0-02`/`P0-03` 很容易做成"又一层塞进上下文的散文"**——`kb/tactics/*` 已经有正确的写法（判定标准 + 不许跳级 + 算不算命中），一旦做成"把整篇 md 灌进 worker"，就会重演 P9-1 之前"43% 输入 token 花在说明书上"的老路，且比不做更慢更贵。
3. **`P0-04` 与 `P1-02` 反过来会制造"任务永不结束"**——现在之所以能手停手，一部分是因为 `prove_goal` 没闸门；一旦装上 E3/E4 闸门又没配上"推不动就写否定结论并收工"的出口，20 分钟模板会变成 1200s×N 的空转（而且审查官的触发条件只认"停顿"，不认"卡在低等级"）。
