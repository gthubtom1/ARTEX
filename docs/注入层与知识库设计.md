# 注入层（可换词）与知识库设计

> 两件事分开说：**知识库**决定"它会不会想到"，**注入层**决定"它敢不敢做"。
> 前者是能力问题，后者是可用性问题。混在一起做会两头都不对。

---

## §0 现状盘点（实测 `RuoJi6/ARTEX` v0.3.18）

| 项 | 实际情况 |
|---|---|
| 技能 | **4 个，共 261KB**：`api-recon`(145K)、`playwright-cli`(88K)、`scopesentry`(20K)、`zero-to-expert`(8K，我加的) |
| 知识库 | **无**。没有 CVE 库、没有 payload 库、没有指纹库、没有向量检索 |
| 案例库 | **无**。任务跑完的 finding/trace 全在 PG 里，但没有沉淀成可复用的"经验" |
| MCP | 有（可外挂），但默认空 |
| 注入层 | **无**。只有 prompt 开头那句授权框架，**不是破甲词** |

结论：**它的"思维广度"完全来自模型自身的先验知识**。模型不知道 ThinkPHP 5.0.23 的具体利用链，它就真的想不出来。这就是"遇到没见过的站就卡住"的直接原因。

先纠正一个误解：ARTEX 自带的那句是

> 「你是一个网络安全平台授权渗透测试系统的"规划者"……」

这是**授权框架**，作用是让模型不把任务当恶意请求，**不是破甲词**，也没有任何拒答规避设计。它每轮重渲染、一直在场（`agent/prompt.go` 的 `renderSystem`）。

## §1 知识库：要加，但**绝不能塞进提示词**

### 1.1 那个 2–3GB 的库是什么

典型构成：`nuclei-templates`（1 万+ YAML，~200MB）、`SecLists`（字典，~5GB）、指纹库（Favicon hash/关键字）、CVE/CWE/CAPEC 元数据、Exploit-DB、自建案例。**这些加起来很容易 2–3GB。**

### 1.2 容量 ≠ 能力（这是最容易踩的坑）

把 30 万 token 的知识塞进 system，结果不是变聪明，是 **context rot**：
注意力被稀释 → 该用的那条没被选中 → 反而比不塞更差，而且每轮都烧钱。

正确做法是 **progressive disclosure（按需检索）**，而且检索必须发生在**具体的判断点**上，不是任务开场。

### 1.3 三个检索点（"思维更广"的真正来源）

| 检索点 | 触发时机 | 问什么 | 返回什么 |
|---|---|---|---|
| **① 指纹 → 已知漏洞** | 刚写下一条含 `tech/version` 的 fact 时 | `ThinkPHP 5.0.23` | 命中 CVE + 默认路径 + 默认口令 + 已知 RCE 链（**最多 5 条**） |
| **② 形状 → 攻击面** | 看到一个 endpoint 的形状时 | `GET /api/v1/user/{id}` | 这类形状常见缺陷清单（IDOR/批量赋值/越权/枚举）+ 检查顺序 |
| **③ 手法 → 最小 payload 集** | 确定 tactic 之后 | `inject/sqli + mysql + 有 WAF` | 3–5 条最小可用 payload（**永不返回全库**） |

这三步对应真人专家的三个动作：**"这个版本有什么洞" → "这个接口像什么毛病" → "给我三条能打的"**。

### 1.4 落成 ARTEX 的形态（**不用写 Go**）

三个**自定义工具**（`系统 → Tools → 新建`，`kind = script` 或 `http`）：

```
kb_fingerprint(tech, version)              → JSON: {cves[], paths[], creds[], chains[]}
kb_surface(method, path, params, auth)     → JSON: {classes[], checklist[], examples[]}
kb_payload(tactic, tech, waf, context)     → JSON: {payloads[3-5], notes}
```

配一个 skill `kb-first`（写清"什么时候必须查、查到什么程度就停"），绑到 `planner` + `worker`。
这样知识库**只在需要时进上下文**，一次 300–800 token，而不是常驻 30 万。

### 1.5 检索实现：用 Postgres 全文检索，不上向量库

- 已有的 PG 直接开 `tsvector` + GIN 索引，中文用 `zhparser` 或 trigram（`pg_trgm`）。
- **不要上向量库**：渗透知识的关键词性极强（版本号、CVE 号、路径、类名），BM25/trigram 又准又可解释，向量反而召回噪声。
- 2–3GB 数据在 PG 里毫无压力，FTS 查询 10–30ms。

### 1.6 数据来源与许可

| 来源 | 许可 | 用途 |
|---|---|---|
| nuclei-templates | MIT | 指纹 + CVE 检测模板 |
| PayloadsAllTheThings | MIT | payload 库 |
| SecLists | MIT | 字典 |
| CWE / CAPEC | 公开 | 缺陷分类 |
| Exploit-DB | GPL-2 | 参考，**注意再分发限制** |
| **自建案例库** | 自有 | ★ 最值钱，见下 |

### 1.7 案例库自动沉淀（这是"越用越强"的唯一来源）

每次任务收尾，把 `finding + 成功路径的 worker trace + 用的 payload + 失败原因` 压成一条 case：

```json
{
  "fingerprint": "ThinkPHP/5.0.23",
  "surface": "GET /index.php?s=captcha",
  "tactic": "rce",
  "payload": "POST _method=__construct&filter[]=system&method=get&server[REQUEST_METHOD]=id",
  "result": "success",
  "waf": "none",
  "time_to_root": "6min",
  "notes": "需要先过 captcha 路由；直接打 index.php 会 404"
}
```

**别人没有这个**：他们能下载 nuclei 模板，但下载不到"你打过的站是怎么打下来的"。
ARTEX 的 `report/` + `traces` 数据已经齐全，加一个导出器即可。

## §2 注入层：可换词、按需注入

### 2.1 为什么做在 provider 层，而不是改 prompt

| 位置 | 能做到 | 做不到 |
|---|---|---|
| 改 `agent_prompts` 正文 | 每轮生效、可换词 | **无法按上下文状态开关**（永远在 or 永远不在） |
| 改 `constraintBlock` | 每轮追加 | 同上，且它是业务约束不是抗拒答 |
| **`llm.Provider` 装饰器** | 每次请求都能决策：注不注、注什么、注多长 | — |

现成模板：`llmrec/llmrec.go:118` 就是一个 Provider 装饰器（Recorder）。照它写。
链序建议：`inner → Recorder → Injector → Pool`（注入内容也进录制，便于复核与审计）。

### 2.2 四种模式（DB setting，可按 agent / 按任务覆盖）

| 模式 | 何时注入 | token 成本 | 适用 |
|---|---|---|---|
| `always` | 每请求 | +300~800 tok/次 | 便宜模型、拒答频繁 |
| **`on-miss`（推荐）** | system 里检测不到注入指纹时 | 极低 | 长任务（防压缩后丢失） |
| `on-refusal` | 上一轮命中拒答特征 | 最低 | 强模型、偶发拒答 |
| `hybrid` | on-miss ∪ on-refusal | 低 | 默认 |

**这就是你说的"上下文里没有了再注入"**，而且判定是确定性的（字符串指纹），不花 token。

### 2.3 注入位置：`req.System` 末尾

```go
// inj/injector.go（新增，约 120 行）
type Injector struct {
    inner  llm.Provider
    cfg    func() Config        // 每次请求读，改设置立即生效
    cache  atomic.Value         // 渲染好的块 + 指纹
}

func (i *Injector) Complete(ctx context.Context, req llm.CompletionRequest) (llm.Message, string, llm.Usage, error) {
    return i.inner.Complete(ctx, i.mutate(req))
}

func (i *Injector) mutate(req llm.CompletionRequest) llm.CompletionRequest {
    c := i.cfg()
    if c.Mode == "off" || c.Text == "" { return req }
    if c.Mode != "always" && alreadyInjected(req.System, c.Fingerprint) { return req }
    sys := make([]string, 0, len(req.System)+1)
    sys = append(sys, req.System...)
    sys = append(sys, c.Rendered)          // 追加到末尾，前半段仍可命中 prompt cache
    req.System = sys
    return req
}
```

**为什么是 System 不是 User**：
1. system 权重最高；
2. 不参与对话轮转，不会被 compaction 折叠（compaction 只处理 messages）；
3. 放末尾 = 离模型最近，遵循度最高。

### 2.4 拒答检测器

`inj/detect.go`，**零 token** 正则层：

```go
var refusalMarkers = []string{
    // 中文
    "我不能", "无法协助", "无法提供", "作为AI", "作为人工智能", "建议您咨询",
    "抱歉", "不适合", "违反", "存在风险", "应联系",
    // 英文
    "i can't", "i cannot", "i'm unable", "as an ai", "i must decline",
    "i won't", "not able to help", "against my", "i apologize",
}
```

命中后：
1. 记一条 `refusal_events(task_id, intent_id, step, marker, ts)`；
2. 下一请求**强制注入**（即使模式是 `on-refusal` 也注）；
3. 仍拒 → 把该错误映射成"可 failover"，`llmpool` 自动切下一个 profile（`shouldFailover` 已有）；
4. 同一 intent 连拒 3 次 → 不再重试，写一条 fact `refused` 交给顾问（**不要无限重试**，那是最常见的空转）。

### 2.5 省 token 的具体算法

- **指纹比对**：注入块前缀 + 不可见标记 `<!--ARTEX-INJ:v3:h8f2-->`，`strings.Contains` 判一次，0 成本。
- **渲染缓存**：`{{.Goal}}` 等变量变了才重渲染，否则复用 `atomic.Value`。
- **只追加不重写**：`req.System` 末尾 append，前半段提示词缓存（Anthropic 的 `cache_control` / OpenAI 自动前缀缓存）仍然命中。
- **长度上限**：单块 ≤ 900 字符，多块最多 3 段（超过就腐坏，收益变负）。

### 2.6 词库设计（兼容任意措辞，和 seep/pi-web 同一思路）

```sql
CREATE TABLE inject_profiles (
  id bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  name text NOT NULL,
  scope text NOT NULL DEFAULT 'global',   -- global | agent:<key> | task:<id>
  text text NOT NULL,
  mode text NOT NULL DEFAULT 'hybrid',
  priority int NOT NULL DEFAULT 5,
  enabled boolean NOT NULL DEFAULT true,
  fingerprint text,                        -- 自动生成的 hash 前缀
  inject_count bigint NOT NULL DEFAULT 0
);
```

- **导入即用**：粘贴任意文本 → 存成一条 profile，不需要改代码。这就是"兼容任何破甲词"。
- **多套并存按 priority 拼接**，上限 3 段。
- **变量替换**：`{{.Goal}} {{.Now}} {{.Constraints}} {{.Tactic}} {{.Target}}`。
- **不外泄**：词库正文不进 report、不进日志、不进导出报表；只记 `name + fingerprint`。这条要写死在代码里。

### 2.7 一个必须防的副作用

注入层会**掩盖真实失败**。模型拒答有时是因为"这步真的做不了"（缺工具、目标不可达、超出范围），注再多词也没用。
所以 `refusal_events` 必须带上下文（哪条 intent、哪个工具、什么参数），交给顾问 agent 判断：
**拒答是"不敢"还是"不能"** —— 前者注入，后者换路线。这个分流不做，注入层会变成噪声放大器。

## §3 接线补丁

| 文件 | 改动 |

| `inj/injector.go`（新） | Provider 装饰器 + mutate + 指纹缓存 |

**知识库部分不需要改 Go**：三个自定义工具 + 一个 skill + 一个导入脚本（把 nuclei/pat 数据灌进 PG 的 FTS 表）。

## §4 验收

| 指标 | 方法 | 期望 |
|---|---|---|
| 拒答恢复率 | 开/关注入各跑 3 次同任务 | 开：拒答后 80% 能继续；关：直接卡死 |
| token 增量 | `on-miss` vs `always` | 前者 < 后者的 30% |
| 能力不劣化 | finding 数对比 | 不减（注入不该影响判断质量） |
| 知识库命中率 | 随机 50 条指纹，看 `kb_fingerprint` 命中率 | ≥ 60%（说明库有用） |
| 案例复用率 | 新任务里引用旧 case 的次数 | 从 0 到 > 0（这是"越用越强"的证据） |

**顺序建议**：注入层先做（2 天，纯装饰器 + 两张表 + 一个页面），因为它立刻减少空转；知识库后做（1 周，主要是数据灌入与检索调优）。两个都做完再回去做顾问 agent 的冻结门——那时顾问手里才有"知识"和"不拒答"两个前提。
