## 2. 待你定（5 条，我给不出唯一答案）

### D-1 `snapshot.Restore` 未接线 →「可回滚」这一半不成立 ★ 建议优先定

**现状**：写文件工具的写前快照**只写不读**（`Restore` 零调用）。`docs/00` 的 D02 决定写着"默认全开，用**可回滚**兜底"——后半句现在是空头承诺。

**两条路**：
- **A. 接上恢复接口**（新功能，约半天）：`POST /api/snapshots/{id}/restore` + 前端一个"回滚"按钮。好处：D02 从口号变成真能力。
- **B. 改掉措辞**（10 分钟）：把 D02 改成"快照用于事后对比，不支持一键回滚；恢复=手工从 `data/snapshots/<id>/` 拷回"。
- 我倾向 **A**，但它是新增功能、要动前端，所以等你点头。

### D-2 `adviser.Steer/Kill` 未接线 → 顾问只会"提建议"，不会动手

**现状**：顾问算出 `steer`（改写某个 worker 的方向）和 `kill`（杀掉跑偏的 worker），但 `progressHook` 只消费 `d.Hints`，`adviser.Apply` 零调用。所以现在顾问**永远不会终止任何东西**。

**两条路**：
- **A. 接上**：让 `kill` 生效（同方向 N 次 0 产出就杀）。好处：真能止损；风险：**误杀**正在接近突破的 worker。
- **B. 保持**：只提建议，由 planner 决定要不要换方向（现状）。
- 我倾向 **B 保持**，因为杀掉一个正在接近突破的 worker 的代价 > 省下的 token。你若想试 A，我可以加一个开关默认关。

### D-3 `enrich` 链构造了但从不读 → 资产图自动补全从未运行

**现状**：`enrich` 引擎被构造、`SetEnrich` 赋了值，但 `t.enrich` 从没被读取。所以资产节点只靠 worker 手写，**DNS 解析 / HTTP 指纹的自动补全一次都没跑过**。

**两条路**：
- **A. 接上**（中等改动）：`insert_assets` 落库后异步补 DNS/HTTP，回写 `attrs`。好处：覆盖率与资产图质量明显提升；成本：每条资产一次 DNS + 一次 HTTP。
- **B. 删掉这条链**：承认"不做自动补全"，删 `internal/enrich` 的接线代码。
- 我倾向 **A**，但它会增加出口流量（每条资产 2 个请求），对你的 token 没影响、对目标有影响。

### D-4 `internal/oast` 未接线 → 盲 SSRF / 盲 RCE 检测不可用

**现状**：库完整（4 单测全绿），但需要一个**公网可达的回调地址**才能工作，笔记本环境无法自证。

**两条路**：你有公网 VPS → 我接上（约 2 小时，含一个 `/oast/` 接收端 + 工具暴露）；没有 → 保留库，标"未接线"（现状）。

### D-5 仪表盘每 15s 拉 3 个无用的接口

**现状**：`api.agents()` / `api.mcpServers()` / `api.skills()` 的结果存进 state 后**零读取**，等于每次刷新白发 3 个请求。

**两条路**：删掉这 3 个调用（前端小改，5 分钟）；或留着（无害但浪费）。我倾向删，只是要动 `dashboard/page.tsx`，所以列在这里。
