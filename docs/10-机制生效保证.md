# 机制生效保证（怎么保证"写了就真的会被用"）

> 回答一个问题：**提示词能不能保证模型用工具？不能。**
> 本文件给出四种"硬度递增"的保证手段，以及每类机制的使用度量与退役规则。
> 依据：任务 #2 实跑数据（45 分钟）。

---

## 0. 实测：写了 ≠ 用了

| 事实 | 数据 |
|---|---|
| 系统里装好的工具 | 11 个常见渗透工具全在（sqlmap/nmap/ffuf/nuclei/hydra/nikto/gobuster/whatweb/masscan/nc/socat） |
| 工具发现机制 | ✅ 正常工作：`[env] tool discovery: 8422 tools` |
| worker 绑定的内置工具 | 45 个，`deferred=false`（schema 每轮可见） |
| 其中三个结构化工具 | `nmap_scan` / `httpx_probe` / `nuclei_scan` 已注册、已启用、worker 可见 |
| **实际调用** | `Bash` 556 次、`curl` 178 次、`python3` 140 次；`nmap` 4 次、`sqlmap` 1 次；**`httpx_probe`/`nuclei_scan`/`ffuf`/`whatweb`/`hydra` = 0 次** |
| 延迟加载（`SearchExtraTools`/`ExecuteExtraTool`） | 94 次，但**只检索元工具**：`get_worker_trace` 29、`get_worker_output` 24、`list_assets` 8、`list_facts` 1 —— **一次都没检索过 nmap/sqlmap/ffuf** |

**结论**：工具在、schema 在、发现机制也在，模型就是不调。它把 `Bash` 当万能逃生门。

---

## 1. 为什么"写了提示词还是不用"（三类原因）

| 类别 | 机制 | 表现 |
|---|---|---|
| **偏好** | `Bash` 是通用工具，一次调用能做任何事；结构化工具要记参数、要解析返回 | 模型选"自由度高"的那个 |
| **热点** | 模型当前的"需求"是"读我自己的 worker 输出"（因为它要汇报进展），不是"扫端口" | 于是 `SearchExtraTools` 搜的全是元工具 |
| **无约束** | 没人要求"不调结构化工具就不算完成任务" | 调不调都不影响它继续跑 |

**所以只加提示词 = 把概率从 3% 提到 15%，不是保证。** 要保证，必须动机制。

## 2. 四种保证手段（硬度递增）

### L1 提示 + 示例（软，只能提概率）

在 worker 提示词里写映射表，并给一条"正确示范"。

```
端口/服务 → nmap_scan（别裸跑 nmap）
存活/指纹 → httpx_probe（别用 curl -I 一个个人工看）
目录枚举 → ffuf（别手写 for 循环）
口令     → hydra
注入/文件读取/带内回显 → 可以手写 curl/python
```

**判据**：改完后同样任务里 `httpx_probe`/`ffuf` 调用数 ≥1。达不到 → 进 L2。

### L2 触发式提示（半硬：在"对的时候"提醒）

在 `guard.preToolUse` 里对 Bash 命令做模式匹配：命令首词是 `nmap|ffuf|dirb|gobuster|hydra|nikto|whatweb` 时，返回一句结构化建议（不阻断）：

```
你正在用 Bash 裸跑 nmap。改用 nmap_scan 会返回结构化 JSON（端口/服务/版本），
省掉解析屏幕文本的 token。要改用吗？（继续用 Bash 也可以）
```

**判据**：同任务 `nmap_scan` 占比 ≥50%（相对裸跑 nmap）。达不到 → 进 L3。

### L3 引擎断言（硬：不给就不算完成）

在 intent 完成的判定里加"必要产出"：

```go
// 侦察类 intent 的完成条件：必须存在至少一条 fact，
// 其来源是结构化工具（source=tool:nmap_scan / httpx_probe / ffuf）
if intent.Stage == "recon" && !hasFactFromTool(taskID, intent.ID, "nmap_scan","httpx_probe","ffuf") {
    return errors.New("侦察意图缺少结构化工具产出：端口/指纹/目录至少各用一次对应工具；" +
        "裸跑 Bash 不计入。若工具不可用，请在结果里注明原因。")
}
```

**代价**：模型可能伪造"工具不可用"。所以配一条**反向校验**：声明"工具不可用"时，引擎用 `envDisc.Find` 核实，实际可用则拒绝该理由。

**判据**：连续 3 个任务，侦察三件套 100% 出现。达不到 → 进 L4。

### L4 引擎代做（最硬：不给模型选择）

开局第一条 intent 由引擎**直接生成并执行**（不走模型决策）：

```
任务创建 → 引擎自动跑：
  nmap_scan(host)      → 写 fact（source=tool:nmap_scan）
  httpx_probe(url)     → 写 fact（source=tool:httpx_probe）
  （若 httpx 发现目录类线索）ffuf(base) → 写 fact
→ 结果作为"开局态势"塞进 planner 的第一轮上下文
```

**优点**：100% 保证；**成本**：每个任务固定多 1–2 分钟 + 少量 token。
**风险**：目标不接受扫描时可能触发 WAF → 需要"探测失败即降级为被动侦察"的分支。

## 3. 四种手段怎么选（不是越硬越好）

| 情形 | 用哪档 |
|---|---|
| 只影响效率、不影响正确性（如用哪个工具扫） | L1 → L2，观察 3 个任务 |
| 影响结果完整性（没有它，后面的利用全是猜） | **L3** |
| 影响可用性（第一个战果都出不来） | **L4** |
| 只是"更优雅" | 不做 |

**默认策略**：侦察三件套走 **L3**（断言），其余走 L2（触发式提示）。

## 4. 每类机制都必须有"使用度量"和"退役规则"

这是过去最缺的一条。**没有度量 = 不知道有没有被用 = 一个月后发现是空表。**

| 机制 | 度量 | 目标 | 达不到怎么办 |
|---|---|---|---|
| 结构化工具（nmap_scan 等） | 每任务该工具调用次数 / 裸跑同工具次数 | 侦察类 ≥1，占比 ≥50% | L1→L2→L3→L4 逐级加硬 |
| 能力卡（`capabilities`） | 每任务写入行数 + `decided` 次数 | ≥3 行，≥1 次裁决 | 若恒 P1 说明派生失效 → 改引擎自动写（生产端钩子） |
| 台账（`assets_owned`） | 有立足点任务里 ≥1 行 | 100% | 引擎自动登记（不靠模型） |
| 证据时间线 | 每 finding ≥1 行 | 100% | 引擎在 finding 入库时写 |
| 案例沉淀 | 每任务 ≥1 条（正/负） | ≥1 | 引擎在收尾时写 |
| 战果清单（会话右栏，原写“地图 tab”） | 打开次数 / 复制下一步次数 | ≥0.5 / 任务 | 若低于 → 说明没人看，砍掉或换入口（**注：tab 与画布已于 2026-10-23 删除，现形是 `_tabs/loot-panel.tsx`**） |
| 审查官（新） | `review_runs` 条数 + `ack_status` 采纳率 | 介入 ≥2，采纳率 ≥50% | 采纳率 <30% 连续 3 任务 → 自动降权为“只看”（已实现：熔断转 observe） |
| 基准（`bench_runs`） | 最近 30 天是否有记录 | ≥1 | 长期 0 → 退役（已被"命中率看板"替代） |

**退役规则**：连续 3 个真实任务，度量未达标且无人在 UI 上用 → **标记为"实验"，从主链路移出**（不删代码，但不进提示词、不进默认面板）。避免"空表越堆越多"。

## 6. 判据（G5 门）

上线后连续 3 个真实任务，必须同时满足：

- `httpx_probe` ≥1 次/任务、`ffuf` ≥1 次（有目录线索时）
- `nmap_scan` 占端口扫描类调用 ≥50%
- `capabilities` ≥3 行且至少 1 次 `decided`
- `evidence_timeline` ≥ findings 数
- `assets_owned` 在有立足点的任务里 ≥1

**任一项为 0，说明对应机制仍是"空表"，不许对外说"已优化"。**
