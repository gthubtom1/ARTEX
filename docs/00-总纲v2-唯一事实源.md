# ARTEX 二开 · 总纲 v2（唯一事实源）

> 写这份文件的原因：`docs/` 下 24 份设计与记录互相覆盖，同一个机制有 2–4 个名字、3 个数字、2 套阈值，
> 结果每次换会话都要重新读一遍并重新裁决。**从现在起，本文件是唯一事实源。**
>
> 裁决顺序：**本文件 > `docs/进度台账.md`（活账）> `docs/最终方案-v1.md`（历史总纲）> 其余 21 份**。
> 与其余文档冲突时以本文件为准，并**不再回头改那 21 份**（它们留作历史，不参与决策）。
>
> 状态口径只有三种，别再用别的词：
> **✅ 主链路真调用｜⚠️ 有代码但主链路缺环｜❌ 只有包/文案，没有消费者**

## 0. 一句话

给一句话 → 自主推进 → 每一步有证据 → 把"能做什么"翻译成白话菜单 → 打下的资产进台账并定期复查 → 出可复现报告。
技术底子是 `planner / worker × 探索图 / 资产图`，二开只做增强层，**不重写运行时**。

## 3. 不可返工的决定（14 条，编号唯一）

前 8 条来自 `RESUME.md`（保留原文语义），后 6 条是本轮新增的裁决。

| # | 决定 | 为什么不能改 |
|---|---|---|
| D01 | **零权限门**：不做开关分级，提示词不出现「禁止/不允许」 | 一旦出现负面文案，模型会在无关步骤上脑补规则并拒执行 |
| D02 | 默认全开，用**可回滚**兜底（写前快照） | 用"禁止"控风险会让模型变笨；用"能撤销"控风险不会 |
| D03 | 目标清单与出口放**网络层**，模型看不见 | 让模型看到"你不许打 X"，等于给它一条拒绝的理由 |
| D04 | 迁移走 `schema_migrations` 账本，runner 剥离文件内 `BEGIN/COMMIT` | 手工 psql 必然会漂 |
| D05 | 表名 `local_tools_cache`（不是 `tools_cache`） | 与 `mcp_tools_cache` / `tools` 混淆过 |
| D06 | `creds_vault` 只存加密秘密本体；`task_intelligence(kind=credential)` 存叙述性情报 | 两套语义混一起会泄密 |
| D07 | 交付物表（capabilities/assumptions/evidence_timeline）任务外键 `SET NULL` | CASCADE 会静默丢证据 |
| D08 | `audit_log` 无外键、只追加 | 审计表不能因为删任务而断链 |
| D09 | 幂等键 = `keyFor(task,intent,step,tool,input)`，重复写回返回"已存在" | 重复写回报错会让 worker 误以为失败而重试 |
| D10 | **注入层挂在 provider 层**（不是改 `agent_prompts` 正文） | 正文改不了"按上下文开关"；provider 每次请求都能决策 |
| D11 | **减法用代码层硬拒绝**（同方向 4 次 0 产出），不用提示词劝告 | 提示词劝告会被"换个说法"绕过；代码拒绝不会 |
| D12 | **能力卡派生自 finding，不独立维护** | 两套真相必然不一致 |
| D13 | 六层架构固定为 §1 那六层，其他分层说法作废 | 分层漂移会导致重复造轮子 |
| D14 | **没有基准跑分就不许说"变强了"** | 24 份文档里所有"更强/更快"的判断，全都没有标尺 |

## 6. 现在真实的能力边界（不许再乐观表述）

**能做的**：本地靶场（DVWA / DSVW / Juice Shop 级）在 1–2 分钟内出首个确认战果；有已知漏洞族的老站点能打到读权限并出 PoC；打下的资产能进台账、能复查、能出报告。

**做不到的**：
1. 现代真实业务站（有 WAF + 业务逻辑复杂 + 无已知 CVE）一把打穿 —— 头部产品也一样（见 `docs/01-零基础实战判定.md` §3）。
2. 全程无人值守：`intercept_auto_decide=off` 时高危动作会挂起等人。
3. "零基础零配置"：仍然必须准备 PostgreSQL + LLM + 出口代理（见 §7）。

**唯一可以把"能不能"变成客观问题的办法**：接一个基准跑分（P8-1）。在这之前，所有强弱判断都是感觉。

## 7. 零基础必须准备的 6 项（当前硬门槛）

| # | 项 | 不填的后果 |
|---|---|---|
| 1 | PostgreSQL 连接（`ARTEX_PG_DSN` 或 `config.json`） | 进程起不来 |
| 2 | 管理员密码（≥8 位） | 无法登录 |
| 3 | LLM：provider + model + api_key（+ base_url） | 任务排队，永不启动 |
| 4 | **宿主层能出网**（VPS 直连；本机打靶场启动时加 `ARTEX_ALLOW_DIRECT=1`） | 任务创建后立刻 `paused`（fail-closed） |
| 5 | 任务描述 | 后端兜底"未命名任务" |
| 6 | 任务目标 `goal` | 后端不校验；空 goal → planner 直接判 done |

> 第 1、2 项在 VPS 上已经由 `scripts/deploy_vps.sh` 一条命令做掉（装 docker + 生成随机 Postgres 密码 + 起服务），
> Windows 用户看 `install.sh` 打印的指引（Git Bash 下 `exit 2` = 需人工介入，不是脚本坏了）。
>
> 第 4 项**不再是应用配置**：D1 已删掉应用内代理，网络在宿主层解决，应用只保留"出口 IP 自检"
> 来发现 TUN 掉线 / 换机房 / 路由泄漏。它仍是最容易踩的坑——宿主出不去网，任务一建就 `paused`，
> 而错误只在活动流里出现一次。
