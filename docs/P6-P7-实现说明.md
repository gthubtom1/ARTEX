## 一、P3 决策队列（三档按钮）

| 文件 | 作用 |
|---|---|
| `internal/decision/decision.go` | 三档裁决的纯逻辑：`evidence`（默认，只拿证据，封顶 P2）/ `continue`（15 分钟 / 20 轮预算，可升 P3）/ `switch`（冻结该资产，转未测资产） |
| `agent/p2.go` `DecideCapability` | 落库（`capabilities.status/decided_*`）+ 写一条规划者能读到的 hint（否则"点了按钮"等于没点） |
| `agent/p2.go` `decide_capability` 工具 | 主 agent / 人机界面可调用 |
| `server/p2_api.go` `POST /api/capabilities/{id}/decide` | 面板写接口；同时写 audit + 活动流 + 唤醒 planner |
| `db/migrations/0002_p3_decisions.sql` | 决策留痕列 + 复查命令列 + `recheck_state` |

**为什么 hint 是必须的**：`planner` 只读图里的节点。裁决只改表不改图 → 下一轮规划完全看不到，等于没裁决。

## 三、P5 复查执行器

| 文件 | 作用 |
|---|---|
| `internal/recheck/recheck.go` | 到期台账 → `ledger.PlanChecks` 生成只读命令（nc/curl）→ 执行 → `RecordCheck` 写回；单条 10s、批次 10、支持注入 Executor 测试 |
| `server/recheck_loop.go` | 启动后 30s 起跑，之后按 `asset.recheck_minutes`（默认 60）轮询；结果写活动日志 |
| `server/p2_api.go` `POST /api/owned/recheck` | 手动"现在查一遍"（批次 20） |

安全：命令只来自 `PlanChecks`，主机/URL 先过字符白名单（`ledger.SafeHost/SafeURL`），脏数据 → `manual` 跳过，不执行。
HTTP 复查用 `curl -w '%{http_code}'`，2xx/3xx 记 verified，其余记 stale。

## 四、P7 注入层

| 文件 | 作用 |
|---|---|
| `internal/inject/inject.go` | 拒答检测（中英措辞）、可换词重定向（4 套，按哈希稳定选择）、执行上下文块、token 预算 |
| `agent/inject_hook.go` | `harness.HookRunner` 装饰器：其他钩子透传，`Stop` 时若最后一条助手消息像拒答且无工具调用 → 注入一条技术重定向并继续（默认最多 2 次） |
| `agent/planner.go` / `agent/worker.go` | 系统提示尾部追加执行上下文（always/hybrid）；planner 钩子由引擎每轮注入 `t.Guard.Hooks()` |
| `server/server.go` | `agent.InjectConfigFor` 从 settings 读 `inject.mode` / `inject.max_chars` / `inject.max_retries` |

配置：`inject.mode = off | always | on-miss | on-refusal | hybrid`（默认 hybrid）。

**on-miss（按需注入）是独立实现，不依赖 guard**：

- 执行上下文块固定带注入指纹 `[[ARTEX-CTX-v1]]`（`inject.Marker`）；
- `internal/inject/provider.go` 的 `Injector` 是 `llm.Provider` 装饰器：**每次请求模型前**检查
  system + 全部消息里还有没有指纹，没有就补一段执行上下文（压缩/截断/续跑丢块后自动补回）；
- `agent.WrapProvider` 按 mode 决定是否挂装饰器：`on-miss/always/hybrid` 挂，`off/on-refusal` 不挂；
- 服务端在 `server/task_llm.go` 把 planner/worker 的 provider 包一层（goal 由任务传入）；
- 预算：每次补注入受 `inject.max_chars` 限制，`Injector.Stats()` 记录补注入次数/字符数。

`guard.ToolPresence` 仍然负责"命令首词不存在时给等价替代建议"，那是另一条通道，与 on-miss 无关。

## 六、P7 多模型分工

平台本来就支持 per-agent LLM 绑定（`taskLLMRuntime{agentKey}` 解析：agent 绑定 → 任务 profile 链 → 全局）。本轮：

- 新增内置 agent **`adviser`（顾问）**：可单独绑强模型；`server/adviser_llm.go` 在检测器命中时调用它，
  输出结构化 JSON 经 `adviser.ParseJSON` 收敛（hint ≤3、不可执行丢弃）；失败/超时自动回落确定性规则。
  冷却：每任务 10 分钟最多一次 LLM 调用。
- 新增内置 agent **`verifier`（校验）**：独立"专判"角色。
  `internal/verifier` 负责提示词与严格 JSON 解析（verified/inferred/rejected + missing[]）；
  `server/verifier.go` 在每轮规划后对**未复核过的 finding** 调一次 `agentKey=verifier` 的模型
  （每任务 5 分钟冷却），结论写 `evidence_timeline(kind='verifier', content_ref='finding:<id>')`，
  幂等（唯一索引 + ON CONFLICT DO NOTHING），并通过 `GET /api/p2/verifier?task_id=` 暴露。
- `planner` / `worker` / `retester` / `adviser` / `verifier` 各自独立 agentKey：
  planner 可绑强模型、worker 绑便宜模型、verifier 绑另一次强模型（或不同厂商）做交叉复核。
- `verify_claim` 仍是零 token 的三门校验；verifier 是"第二视角"，两者互补，不互相替代。

## 七、P7 回放看板（轻量版）

`GET /api/replay/compare?a=<task>&b=<task>`：对比两个任务的意图/事实/发现/hint/token/时长，
以及 发现/意图、事实/意图、token/发现 三个效率指标，返回 `delta` 与一行中文摘要。
页面 `/system/replay`。

**边界**：这是"指标回放"，不是"同 transcript 逐 token 重跑"。后者需要 transcript 重放执行器，未做。

## 十一、本轮补齐（L3/L4 执行面 + 自动裁决 + 真回放）

> 对应《总体方案-黑客工具化升级》的 L2→L4 与"五个放大器"；全部有单测、已接入 agent 工具或 API。

| 能力 | 实现 | 入口 |
|---|---|---|
| M15 数据定位 | `internal/dataloc`：解析 MySQL/PostgreSQL/SQL Server 输出，产出表/行数/敏感列，分级 D1–D4（D4 只标注不执行）；样本打码 | `data_locate` 工具、`POST /api/data/locate`、`/function/data` 页 |
| M12 凭据收割 | `internal/harvest`：配置/历史/env/AK-SK/私钥/云元数据 → 凭据信号；写加密库时不回显明文 | `cred_harvest`、`cred_stale_scan` 工具 |
| M18 自动裁决 | `internal/reviewer` 规则（越界/破坏性→deny，只读→allow，其余→ask）；`guard.AutoDecide` 钩子在**规则命中 ask 之前**生效；任务 allow/deny 约束从 ctx 的 TaskID 读取并参与判定；`allow_all` 直通，`off` 原行为 | 系统设置页"拦截自动裁决"三档、`PUT /api/settings`、audit 的 `auto_allowed/auto_denied` |
| 案例沉淀 | `internal/cases`：正/负结论 → `kb/cases/*.md`（sha 去重）；任务判定达成时 `doneHook` 自动触发 | `POST /api/cases/collect?task=`、`GET /api/cases`、任务完成自动 |
| verifier 联动 | `rejected→P1`、`inferred→≤P2`、`confidence=inferred`，证据追加 `[verifier:…]`，活动流标注已降档 | 自动（每轮规划后） |
| 决策批量 | `POST /api/capabilities/decide-batch`（≤200 条，逐条复用单卡逻辑）；能力菜单页多选 | 前端按钮 |
| M21 真回放 | `internal/replay`：transcript→步骤；只读白名单（curl GET/nmap -sV/nc -z/dig…）重放 + 行重合对比；写操作跳过 | `GET /api/replay/sessions|session`、`POST /api/replay/rerun`、回放页 |
| L3/L4 执行面 | `internal/execx` 策略 + `internal/remote` 远程执行：`privesc_run`/`cleanup_run` **必须在会话上执行**（ssh/db/webshell，秘密只走环境变量），`session_exec` 让 B worker 直接复用 A 的会话；`lateral_run` 从操作机发起建立立足点；成功后登记 owned/session/routes | `session_exec`、`privesc_run`、`lateral_run`、`cleanup_run` |
| 立足点持久化 | 会话写 `access_refs`（conn jsonb），服务启动 `LoadSessions` 恢复；`session_list` 跨 worker 可见 | 自动 |
| 凭据闭环 | `cred_reuse_run`：解密凭据 → 按端口试 ssh/mysql/postgres/redis → `MarkUsed`/`SetVerified`；秘密不回显 | `cred_reuse_run` |

安全边界：
- 数据定位**只解析文本**，不执行 SQL；探测模板只含 `information_schema`/`COUNT(*)`/`LIMIT 1`，无 dump/全表/写语句。
- 真回放只跑白名单只读命令，危险词（rm/sqlmap/mysqldump/重定向/反弹 shell…）一律跳过。
- 清理命令只允许删文件/删账号/清 crontab/停服务，系统根路径拒绝；失败不标 cleaned。

打包：`bash scripts/package_local.sh <版本>` → `dist/artex(.exe)`（前端内嵌，无需 rsync）。

补充（审计后修复）：

- 决策预算熔断：`capabilities.budget_*`（迁移 0003）；`server.enforceBudgets` 到点标 done、写 hint、kill 匹配意图。
- 案例被消费：`cases.Search` + planner 本轮输入注入（`renderRelevantCases`）。

运行时验收（真 PG18 + 本机服务）：
- 迁移 0001–0003 自动应用；`/api/capabilities`、`/api/owned`、`/api/p2/verifier`、`/api/data/locate`、`/api/report`、`/api/knowledge` 均 200；报告含能力菜单。
- `POST /api/owned/recheck` 对本地 200 目标 → `checked=1 ok=1 verified=1`，台账 `last_verified_at` 更新。
- fail-closed：把出口指向死端口后新建任务 → DB 状态 `paused`，活动流记录 `出口未就绪，任务已暂停（fail-closed）：… proxyconnect tcp 127.0.0.1:7999 refused`。
- `ARTEX_PG_DSN=... go test ./... -count=1` → exit 0（Windows 无 sed/POSIX python 的用例显式 skip）。

修复的真实数据库互操作缺陷（冒烟/回归测试发现）：
- bigint[]/text[] 不能直接 Scan（source_node_ids/used_on）→ `array_to_json(...)::text` + json.Unmarshal；写入用 `{}` 字面量 + `::bigint[]`。
- jsonb 参数（audit_log.meta、evidence_timeline.meta）需 `::jsonb`；audit task_id 用 `$1::bigint`（0 与大值都安全）。
- 部分唯一索引（creds fingerprint、asset_checks check_key）ON CONFLICT 必须带 `WHERE` 谓词。
- 复查 URL 要带端口；失败后 30 分钟重试而不是等满周期。
- 新增 9 个 PG 回归用例覆盖上述路径。

审计后补强：
- 预算熔断真正生效：修复 `enforceBudgets` 的 5 列扫描错位；新增 `budgetExpired`（分钟/轮数任一用尽）与 `countRounds`，单测覆盖；到点标 done + hint + kill 匹配意图。
- 扫描工具出口闸：nmap/httpx/nuclei 的 `runAdapter` 现在同样先过 `egress.Guard` 并注入代理环境变量，与 execx/remote/recheck/replay 一致 fail-closed。

实机验收（2026-10-22，本机）：
- 靶场：GitHub `stamparm/DSVW`（单文件 Python 靶场，http://127.0.0.1:65412）。
- 模型：`openai` 兼容端点 cpa / `deepseek-v4.1-flash`（运行时 env 注入，不写仓库）。
- 任务 1：总时长 93s，**首次确认战果 81.9s**，2 个 critical finding（domain 参数命令注入 RCE、id 参数 SQL 注入并可读 users）。
- 任务 2：总时长 64.8s，首次战果 56.5s，2 finding（RCE critical、路径遍历 high）。
- 任务 4（显式要求 record_capability/owned_register/owned_check）：总时长 85.8s，**首次战果 52.1s**；2 张能力卡（4.1/5.1，P3）、1 条持有台账（127.0.0.1:65412 webshell，status=verified）、报告同时含"能力菜单"与"持有资产台账"。
- 结论：标准 1 实测为分钟级（本地公开靶场 + 真实模型）；本地目标直连（ARTEX_ALLOW_DIRECT=1），公网目标仍走代理 fail-closed。
