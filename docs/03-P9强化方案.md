## 1. 为什么"工具少"不会削弱它（D3 的依据）

### 1.1 官方结论（不是我的猜测）

Anthropic / OpenAI / MCP 三家的文档口径一致：

- **50 个工具的 schema 就要 10–20K token**；我们实测 planner 59 个 = 52,312 B ≈ **13,078 token/轮**，worker 48 个 ≈ 9,592 token/轮。
- **一次挂超过 30–50 个工具，工具选择准确率会下降** —— 也就是说工具越多，模型越容易挑错工具。
- 正确做法不是删，是 **progressive discovery / deferred loading**：常驻只留核心几个，其余按需"搜索→加载→注入到上下文末尾"，命中缓存不失效。

我们的账单也印证了这一点：25 分钟任务 813k 输入，**约 43% 是工具说明书**（35 轮 × ~10k），而模型实际用到的只有 18 个工具、其中 5 个是新增的。

### 1.2 我们的实现路径（零新概念，仓库已有半套）

仓库已经有延迟加载机制：`DeferredInfo{GlobalNames, Deferred, Unlock}` + `deferredSystem()` 把
`<available-deferred-tools>` 渲染成**最后一段 system**（可缓存）+ `actool.UnlockSet` 做调用闸。
现在只被 MCP 工具用，**内置工具一个都没用上**。

P9 做两件事：

**(a) 按任务状态挂载（不需要模型做任何动作）**
`P2WorkerTools()` 每次 run 重新计算，加一层"状态门"：

| 工具组 | 什么时候挂 |
|---|---|
| 上报/读态势（report_finding / record_fact / record_capability / list_capabilities / verify_claim / insert_assets / node_detail / get_worker_trace …） | **永远挂** |
| cred_*（5 个） | 任务里出现过 `assets.auth` 或有 `credentials` intelligence 时 |
| session_*（5 个） | 台账里已有 foothold 或当前 run 拿到 shell 时 |
| owned_*（6 个） | `assets_owned` 有该任务的行时 |
| privesc_* / lateral_* / route_* | 有 foothold **且**有凭据时 |
| data_locate / data_mask | 有 `vulnclass` 命中 dataloc 的 finding 时 |

查不到状态（DB 异常）→ **fail-open 全挂**，宁可多花 token 也不能让功能消失。

**(b) 延迟加载兜底**
被状态门挡掉的名字仍然出现在 `<available-deferred-tools>` 里，模型知道它们存在；
配一个 `unlock_tool(name)` 元工具（复用 `UnlockSet`）在需要时拉进来。
这样"工具少"不等于"能力少"。

**预期收益**：worker 41 → 常态 ~12，schema 9.6k → ~4k；planner 28 → ~12，13k → ~5k。
一次 25 分钟任务省 **20–30 万输入 token**。

## 5. 完工后的全量审查（4 个视角，并行）

代码写完不算完。**上一轮的教训是：不同缺陷只能用不同视角抓**，所以审查必须换视角，不能重跑同一个检查。

| 审查员 | 视角 | 必须回答 |
|---|---|---|
| R1 链路 | 页面 ↔ 路由 ↔ 数据源 ↔ 工具名，全量交叉 | 有没有"页面加了导航没注册""路由注册了没人调""工具注册了永远挂不上" |
| R2 契约 | 前后端字段/单位/枚举 | 有没有"同一字段两种单位""前端读了后端不返回的键""同名不同义" |
| R3 行为 | 真跑一次（真模型 + 公网靶场），只查数据 | 工具调用分布、tool_result 膨胀、token 账单、有没有"加了但 0 调用"的功能 |
| R4 交付 | 克隆→部署→跑通，在干净目录 | 缺文件、缺迁移、缺文档、缺权限、Windows/Linux 差异 |

**R4 是一次 `git clone` 到临时目录 + 跑 `install.sh` + `accept_all.sh`** —— 这是唯一能发现
"东西不在仓库里"的视角（bench 那次就是这么露的）。

审查输出要求：**每条问题必须带"复现步骤 + 归属（代码/文档/测试）+ 判定（bug/设计缺陷/可以不改但要知道）"**，
不许只写"建议优化"。审完一次性列全，再决定改哪些，避免又来一轮。

## 6. 一句话总结

D1 删网络管道、D2 关两个哑火角色、D3 用"按状态挂载 + 延迟加载"替代删工具，
再补上"上下文裁剪 / 一键部署 / 指定模型不许换"三块外部验证过的短板，
最后用 4 个不同视角审一遍全仓 —— 这一轮之后不再靠"想到哪改到哪"。
