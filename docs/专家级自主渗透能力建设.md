# 专家级自主渗透能力建设（竞赛向）

> 目标：**给它一个目标，它能像资深红队一样判断"下一步该干什么"**——打点 → 拿 shell → 提权 → 横移 → 拿库/管理员 → 留证据。
> 前提：授权范围内的靶机/竞赛环境。
> 本文先给研究结论（有出处），再给 ARTEX 的 5 个结构性缺口，再给目标架构与竞赛策略。

---

## §1 先说结论：现在全世界最强的系统也做不到"一句话拿全"

2025–2026 的公开评测与论文给出的事实：

| 事实 | 出处 |
|---|---|
| 多 agent 渗透系统失败原因中 **42% 是上下文退化**（context degradation），不是模型不会 | ChainPen (ACM 2026) |
| 三大失败模式：**策略僵化 / 上下文遗忘 / 命令幻觉** | PENTESTLLMAGENT (IJCAI 2026)，基于 13 台 VulnHub + 93 子任务 |
| 黑盒场景下**攻击图一开始不存在，必须增量构建**；平铺的 findings 列表不足以推理 | MazeRunner (arXiv 2608.14216) / "Thinking in Graphs" (Neo4j exploit-chain reasoning, 2026) |
| 有效做法是**专业分工 + 每个目标一个全新上下文 + 状态落盘（不落内存）** | Decepticon（多 agent：recon/exploit/postexploit/analyst…，"fresh context per objective"） |
| 商业/开源横向对比：Strix、PentAGI、Shannon、Claude Code 在同一漏洞应用上差异显著，**没有一家能稳定全自动打穿** | Escape 基准测试；Sauer 实地评测；"Evaluation of Pentesting Agents" (arXiv 2605.10834) |

**所以竞赛里赢的不是"AI 更聪明"，而是：更少跑偏、更少浪费、证据更齐、关键一跳不丢。**
这恰好是工程能解决的问题，也是本文要做的。

## §2 ARTEX 的 5 个结构性缺口（对照"资深红队"）

| 缺口 | 现状（代码事实） | 专家会怎么做 | 后果 |
|---|---|---|---|
| **G1 没有阶段门** | intent 就是一句自由文本，`add_intent` 不校验"你现在有没有资格做这件事" | 没拿到 shell 就不谈横移；没提权就不谈 dump | 会在"还没立足"时就去试内网，全部空转 |
| **G2 没有可达性模型** | 资产图只有 `domain/ip/service/endpoint` 父子关系，**没有 pivot / route / 可达段** | 用跳板把不可达变可达 | 内网永远打不到，横移无从下手 |
| **G3 没有立足点池** | `shell_open/shell_send` 是 SDK 的**会话级**工具，每个 worker 是独立 run，**PTY 不跨 worker 共享** | 所有 worker 共用一个 session 池 | 一个 worker 拿的 shell，另一个 worker 用不了；长连接必断 |
| **G4 没有凭据复用引擎** | 有 `insert_assets.auth` 和 `record_intelligence`（凭据），但没有"凭据→能打哪→验证→复用"闭环 | 拿到密码立刻试 22/3306/admin | 凭据烂在图里，横移缺最关键的一环 |
| **G5 没有后渗透阶段** | worker 结束即止，没有"保持通道"的概念 | 留最小通道、持续利用 | 只能"打一下就走"，做不了"拿全" |

> 一句话：**ARTEX 是优秀的"打点系统"，不是"战役系统"。** 打点靠 planner/worker 就够，战役需要上面这 5 样。

## §3 目标架构：OPPLAN + 能力图 + 立足点池 + 路由

```
goals ──▶ OPPLAN(阶段状态机) ──▶ planner ──▶ frontier ──▶ worker
             ▲  阶段门/前置校验                              │
             │                                              ▼
        adviser(纠偏) ◀──── 停顿检测 ────────────────  能力图(capability)
                                                            │
                         立足点池(session pool) ◀───────────┤
                         路由表(route table)   ◀───────────┘
```

### 3.1 OPPLAN：阶段状态机（治 G1）

阶段固定 8 个，**不可跳**：

```
recon → access → foothold → privesc → pivot → lateral → objective → persist(可选)
```

- 每个 `intent` 必须声明 `stage` + `requires`（前置能力）。
- `addOneIntent` 里加**硬校验**（和冻结门同一处）：

```go
// 阶段门：intent 声明的阶段必须有前置能力，否则拒绝派单
if !t.ts.StageAllowed(t.taskID, it.Stage, it.Requires) {
    return 0, fmt.Errorf("阶段门拒绝：当前能力不满足 %s 的前置（%v）。先完成前置阶段，或改用当前阶段可做的手法。", it.Stage, it.Requires)
}
```

- 阶段推进由 `prove_stage(stage, evidence_node)` 完成（复用 `prove_goal` 的模式），**必须有证据**。
  例：`foothold` 的证据 = 一条带真实命令输出的 trace；`pivot` 的证据 = 一条经代理打通的请求。

### 3.2 能力图（治 G2/G4，也是"Thinking in Graphs"的核心）

**把 finding 翻译成"我现在能做什么"**，而不是"我发现了什么"：

```go
type Capability struct {
    Kind  string // shell | creds | file_read | file_write | db | admin | net_reach
    Host  string
    Level string // user | root | ...
    Via   int64  // 产出该能力的 finding/intent id
}
```

映射规则（`classify(finding)`，CWE 优先、标题关键词兜底——与 apPosture 的 capability 推断同思路）：

| finding 类型 | 能力 |
|---|---|
| RCE / 上传执行 / 命令注入回显 | `shell` |
| 任意文件读取 | `file_read`（读配置→`creds`） |
| SQL 注入可读 | `db`（读用户表→`creds`） |
| 弱口令 / 默认口令 | `creds` |
| 后台进得去 | `admin` |
| SSRF 可出站 | `net_reach`（只算半跳，**不等于 shell**） |
| 提权成功 | `shell(root)` |

**关键规则**：能力一旦产生，**立刻解锁新阶段**，并把它能触达的目标写进资产图（作为 `reachable` 边）。
这就是"打下一个子站 → 它连着的内网就变成可达"的建模方式。

### 3.3 立足点池 + 路由表（治 G3/G5）

新表两张：

```sql
CREATE TABLE footholds (
  id bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  task_id bigint NOT NULL, host text NOT NULL, user_name text,
  proto text,            -- ssh | reverse_shell | webshell | meterpreter
  access jsonb,          -- 连接参数（不含明文口令，口令走凭据池引用）
  proxy_port int,        -- 本机 socks 端口（chisel/ligolo/ssh -D）
  reachable_cidrs text[],-- 从这台机器能到哪些段（来自 ip route / arp）
  status text,           -- up | down | lost
  created_at timestamptz DEFAULT now()
);

CREATE TABLE routes (
  id bigint PRIMARY KEY GENERATED ALWAYS AS IDENTITY,
  task_id bigint NOT NULL, cidr text NOT NULL,
  via_foothold bigint REFERENCES footholds(id),
  proxy_endpoint text,   -- socks5://127.0.0.1:1080
  hops int DEFAULT 1,
  status text DEFAULT 'up'
);
```

**执行侧统一入口**：所有命令的 egress 由 `resolveRoute(targetIP)` 决定，而不是现在"全局一个 `proxyEnv`"：

```go
// 取代 agent/worker.go 里写死的 proxyEnv(proxyAddr, caCert)
env, needProxy := routeEnv(taskID, target)   // 命中 routes → 注入对应 socks + NO_PROXY
```

这一步做完，"横移"才真正可用：worker 不知道也不关心自己在第几跳。

### 3.4 专业分工（治"上下文退化 42%"）

照 Decepticon 的做法：**每个目标一个干净上下文，状态落盘不落内存**。
ARTEX 已有 `agent_prompts` 多 agent 机制，加 3 个角色即可：

| 角色 | 职责 | 工具面（窄） |
|---|---|---|
| `recon` | 端口/服务/子域/指纹 | nmap/nuclei/ffuf + 写资产 |
| `exploit` | 单一入口的漏洞验证与打点 | Bash/WebFetch + report_finding |
| `postexploit` | shell 后的提权/横移/凭据 | session 池 + 提权清单 + 路由 |
| `analyst` | 报告与链组合（现状 `reporter` 已接近） | 只读 |

**为什么必须拆分**：一个 worker 同时想"打点+提权+横移"，上下文必然腐坏——这是论文里 42% 失败的主因。

## §4 专家决策表（把"资深黑客的感觉"变成查表）

这张表是 planner/adviser 的核心资产，**按当前能力直接跳到该做的事**：

| 当前状态 | 下一步（按优先级） | 禁止 |
|---|---|---|
| 只有 web 面 | 指纹→已知漏洞族→最小验证；找第二个身份测越权 | 一上来就跑全量字典 |
| 有 `file_read` | 读配置→拿凭据→换 `creds` | 继续找文件读取点 |
| 有 `creds` | 同段 22/3306/5432/后台各试一次（≤3 目标） | 拿一个密码喷全网 |
| 有 `shell(user)` | 5 分钟固定动作（sudo -l/SUID/cron/配置/内网位置） | 继续在 web 上找洞 |
| 有 `shell(root)` | dump 目标库 / 找 flag / 建第一跳代理 | 停在这里庆祝 |
| 有 `net_reach`（SSRF） | 只用来打内网 HTTP，**不要当 shell 用** | 直接宣布横移成功 |
| 有 `pivot` | 扫新段（-sT）→ 找下一个入口 → 递归 | 一次铺开整个 /16 |
| 目标含 flag/DB/管理员 | 优先走"最短可达路径"，不是"最优雅漏洞" | 追求完整利用链 |

### CTF/竞赛专用启发式（这是拿分的关键）

1. **flag-first**：目标是拿 flag，不是拿 shell。拿到 shell 后第一件事是找 flag（`/root`、`/home/*`、环境变量、数据库、备份文件），不是提权。
2. **3 跳原则**：一条思路超过 3 跳还没实证，降级；竞赛里时间比完美重要。
3. **每 10 分钟 checkpoint**：有 shell 吗？有新凭据吗？有新网段吗？三问全否 → 强制换向。
4. **证据优先**：每次成功立刻留 PoC（请求/响应/命令输出），评分看的是可复现证据，不是你"说打通了"。

## §5 工具链必须补（否则上面全是空谈）

ARTEX 官方镜像只有 `nmap/curl/dig/nc/telnet/whois/jq/rg/node/playwright`。竞赛要用的：

```dockerfile
# 建议单独一层 toolbelt（或用 kali-rolling 基础镜像）
apt-get install -y --no-install-recommends \
  ffuf gobuster feroxbuster nuclei sqlmap hydra john \
  chisel proxychains4 sshpass \
  smbclient ldap-utils nbtscan \
  postgresql-client default-mysql-client redis-tools \
  python3-pip && pip install impacket netexec
# 可选（体积大，按需）：metasploit-framework、ligolo-ng、bloodhound.py
```

**代理与隧道是横移的命门**，`chisel` + `proxychains4` + `ligolo-ng` 三件套必须预装，
并且 `proxychains4.conf` 要能被 `routes` 表动态改写（每任务一份）。

## §6 落地路线（4 阶段，逐阶段可验收）

| 阶段 | 内容 | 验收（拿竞赛同款靶机跑） |
|---|---|---|
| **P0**（3 天） | 阶段门（G1）+ 能力图（G2 前半）+ 决策表进 prompt | 不再出现"没 shell 就试内网"的意图；能力图节点数 > finding 数 |
| **P1**（4 天） | 立足点池 + 路由表（G3）+ toolbelt 镜像 | 一个 worker 拿的 shell 另一个 worker 能直接用；经代理打通 1 台内网主机 |
| **P2**（3 天） | 凭据复用引擎（G4）：creds → spray ≤3 → 验证 → 入池 | 一条密码能自动试 22/3306/后台并记录结果 |
| **P3**（3 天） | 专业分工拆 agent（recon/exploit/postexploit）+ 后渗透阶段（G5） | 同任务 token 降 30%，提权成功率上升 |

**加上之前三轮的产出，完整顺序**：
`注入层(2d) → 知识库(已建) → 顾问+冻结门(3d) → 阶段门+能力图(3d) → 立足点+路由(4d) → 凭据引擎(3d) → 分工(3d)`

## §7 竞赛策略（比技术更影响名次）

1. **先摸底 15 分钟**：所有靶机先 `nmap -sT -p- --min-rate 1000` 一遍，建一张全局表，**按"最短路径"排序**打，不要按题号顺序。
2. **一台机器不超 40 分钟**：超时就冻结，换下一台；全局进度优先于单点完美。
3. **保留一条可用通道**：任何时刻至少有一个能执行命令的立足点（哪怕 www-data）。丢了就回去重建。
4. **评分对齐**：多数竞赛按"flag 数 + 报告质量"计分——**没拿到的写"已确认但未利用"+ 证据**，比空白强。
5. **禁止动作**：不要打范围外 IP、不要 D 服务、不要用真实勒索/持久化手法、不要上传破坏性 payload。判违规直接零分。

---

## §8 一句话总结

**ARTEX 已经解决了"怎么打一个点"，缺的是"怎么打一场战役"。**
战役的四个要件是：**阶段不许跳（门）、能力要能推理（图）、通道要能复用（池）、凭据要能流转（引擎）**。
把这四个补上，再加上注入层/知识库/顾问，它才从"AI 打点器"变成"AI 红队"。
但请记住 §1：即使全部做完，它也不是"一句话拿全"——它是"一句话之后，比你更少犯错的那个队友"。
