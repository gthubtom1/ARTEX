# 复盘官 · 闭环协议与防抖（逻辑定稿）

> 这份文件回答三个问题：①它发给主 Agent 的话，主 Agent 要不要照做？②它会不会越说越乱、把任务带崩？③它自己要不要先复核一遍自己。
> **本文是复盘官交互逻辑的唯一事实源**；与 `docs/09`（数据/接口规格）冲突时，以本文的"流向与权责"为准。

---

## 0. 五条核心原则

1. **复盘官只提建议，不下命令。** 它没有执行权；执行权在「三档权限 + 主 Agent + 人」手里。
2. **主 Agent 必须先核对再决定。** 收到建议后要读当前态势，输出「接受 / 拒绝 + 理由」，不许直接照做。
3. **只有"状态变了"才说（edge-triggered）。** 同一件事没变化就不重复说；重复=噪音=把任务带乱。
4. **说错一次要付代价。** 被拒绝的建议记负反馈，同类建议降权（少发、或只留红点不发）。
5. **有熔断。** 连续介入而任务没变好 → 它自己闭嘴，转"只看"，并在界面说明原因。

---

## 1. 消息流向（谁跟谁说）

```
            ① 复盘官自己看一眼（条件/定时/手动）
                      │
                      ▼
            ② 自检五问（见 §3）── 不过 ──> 丢弃（不投递、只记内部日志）
                      │ 过
                      ▼
        ③ 投递方式按「影响面」分两级
             ├─ A 级（只读结论）：写进复盘官自己的会话 + 按钮亮红点
             └─ B 级（要动任务）：给主 Agent 发一条**建议消息**（不是指令）
                      │
                      ▼
        ④ 主 Agent 核对现状（graph_overview / list_findings / 看 intent 状态）
             ├─ 接受 → 执行（或交给人执行）→ 回执「接受 + 依据 + 做了什么」
             └─ 拒绝 → 回执「拒绝 + 理由（哪条现状与建议冲突）」
                      │
                      ▼
        ⑤ 回执写回 review_feedback：
             接受 → outcome 3 轮后回填 effective / neutral
             拒绝 → 记 negative，同类建议进入降权（见 §4）
                      │
                      ▼
        ⑥ 复盘官下次介入时，**先读自己的笔记 + 被拒历史**，再决定要不要再提
```

**关键**：A 级永远安全（只读）；B 级才可能动任务，而且必须过主 Agent 的核对。

---

## 2. 主 Agent 的核对协议（写进 mainagent 提示词）

收到复盘官消息时，主 Agent 必须按这四步说话，**不许直接调用动作**：

1. **读现状**：`graph_overview` + `list_findings`（必要时看目标 intent 的 `state` 与 `task_error_events`）。
2. **对照**：这条建议里说的现状，和现在库里的一致吗？
   - 一致 → 进入 3
   - 已过期（它说的是 2 轮前的情况）→ 回执「已过期，当前是 X」
3. **判断影响**：这条建议会让你改目标 / 改数据 / 收工吗？
   - 会 → **不许自己执行**，把建议连同理据一起抛给用户（红点不消）
   - 不会（只涉及重开/标死某条意图）→ 进入 4
4. **回复固定三行**：
   ```
   结论：接受 / 拒绝 / 已过期
   依据：<引用的真实 id 与状态，例如 intent#70 state=blocked error=self_error>
   动作：<接受时说明做了什么；拒绝时说明为什么不该做>
   ```

**禁止**：把复盘官的话当命令直接执行；把它的建议当证据写进 findings；因为它说"收工"就收工。

---

## 3. 复盘官的自检五问（投递前）

任一条不过 → 本次不投递（只进它自己的日志，不进主会话、不亮红点）：

1. **重复吗？** 去重键 `(动作类型 + 目标id + 理由类别)` 是否已存在？存在且状态未变 → 不说。
2. **过期吗？** 这条依据的 `intent.state` / `finding` 在上次投递后变过吗？变了 → 重新判，别发旧的。
3. **有依据吗？** 每条结论是否引用了真实 `intent/finding/fact` id？没有 → 标"猜测"，不进 B 级。
4. **是"我的事"吗？** 它只能建议"方向/动作"；判真假（verifier）、改目标、收工都不是它该说的 → 过滤掉。
5. **说了有用吗？** 这条建议被拒过 2 次且证据没变 → 不再重复提（只保留在笔记里）。

## 4. 防抖（防止越跑越乱）

| # | 规则 | 参数 |
|---|---|---|
| R1 | **只对变化说话**：同一 `(动作类型, 目标id)` 在状态未变前只发一次 | 去重键落库 |
| R2 | **冷却**：两次投递最短间隔 | 5 分钟 |
| R3 | **配额**：每任务介入次数上限 / 自动动作次数上限 | 介入 ≤10 / 自动 ≤5 |
| R4 | **降权**：同类建议被拒 2 次 → 不再投递 B 级，只留 A 级红点 | 按 `reason_class` 计 |
| R5 | **自动档只做"减浪费"**：重开被我方故障打断的路、标死目标拒绝 ≥3 次的路；其余全部留红点等人 | 三档设置 |
| R6 | **无改善即收声**：自动动作 ≥3 次且 3 轮内 fact velocity 未上升 → 转 observe（只留红点） | 熔断 |
| R7 | **不碰证据层**：不得删 findings、改 severity/status、改 goal | 硬约束 |
| R8 | **回执义务**：每次自动动作都要写"做了什么 + 依据"，面板可见 | 审计 |

**会不会越跑越乱？会。** 典型回路是：复盘官重开被我方接口搞死的意图 → planner 又派同一件事 → 再次 self_error → 又重开。R1+R3+R6 就是掐这个回路的。

## 5. 结论生命周期

```
drafted ──自检五问──> (drop)
   │
   ▼
sent(read-only) ──> seen ──> (人/主 Agent 处理)
   │
   └──B级──> sent(to main) ──> accepted ──> applied ──(3轮)──> effective | neutral
                          └──> rejected ──> negative(降权)
                          └──> stale（已过期）
```

## 6. 权责边界（一张表说清）

| 谁 | 能做什么 | 不能做什么 |
|---|---|---|
| 复盘官 | 读快照/笔记、出建议、在"低风险档"下执行重开/标死、留回执 | 改目标、改数据、收工、删洞、改严重度、当命令下发 |
| 主 Agent | 核对现状、执行被接受的动作、回执 | 把建议当命令照做、把建议当证据入库 |
| verifier | 判单条洞真假 | 判方向 |
| 人 | 一切（含收工/换目标/改数据） | — |


## 8. 验收判据（可机检）

1. 同一 `dedupe_key` 在状态未变时只产生 1 条 B 级投递。
2. 连续 2 次被拒后，同类建议不再产生 B 级投递（只亮红点）。
3. 自动动作 ≤5 次/任务；触发 R6 后 `review.tier` 变 observe 且界面有说明。
4. 主 Agent 对每条 B 级建议都有 `ack_status`（不允许沉默）。
5. 复盘官的任何执行都不产生 findings/severity/goal 的变更（库层断言）。
