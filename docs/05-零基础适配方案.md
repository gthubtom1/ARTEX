# 二开优化方案（基于实测，终版 v2）

> 本文替代 `05-零基础适配方案.md`（v1，已作废：那一版有 4 处重复造轮子，另有一处事实指控错误）。
>
> 依据：任务 #2 实跑 45 分钟 / 20M input token / 13 轮 / 4 条 finding / 3 类 的真实库数据。
> 方法：把二开声明的每个机制拿去问一句「这次跑的时候它写了吗」。写不了的就是没接上。

---

## 0. 一句话结论

**二开不是"做得不够"，是"做在了模型不会走、人也不会走的那条路上"。**

- 22 个增强机制里，**11 个在 45 分钟的真实任务里一行数据都没写**（台账/路线/假设/证据时间线/案例/情报/技能/基准）。
- 唯一一个交互式控制面（三档裁决）**一次都没被按过**（`capabilities` 2 行，`decided_at` 全空）。
- 真正生效的只有 2 个：凭据收割（1 条）、复查登记（1 条）。

根因不是设计水平，是**接线位置错了**：

| 断点 | 表现 | 证据 |
|---|---|---|
| **生产端断** | 机制写成"工具"，等模型自觉调用 | 45 分钟里 `Bash` 556 次，`record_capability` / `owned_register` / `route_resolve` / `record_assumption` / `bind_finding_traffic` **各 0 次** |
| **消费端断** | 机制页面在人不会去的第二栋楼 | 人在「会话/发现/报告」；二开界面在「能力菜单/台账/资产覆盖图/任务情报」；三档裁决 0 次点击 |

**所以二开优化＝改接线，不是加机制。** 一句话：**贴着引擎已有的事件自动写，贴着人已有的路径自动送。**

## 2. 把 11 个空表分成两类（决定怎么修）

### A 类：本来就该引擎自动写，却交给了模型（6 个）

| 机制 | 应该由谁写 | 现在的触发条件 |
|---|---|---|
| `evidence_timeline` | **引擎**：`record_fact` 成功 / finding 确认时各插一条 | 等模型调 |
| `finding_traffic_bindings` | **引擎**：`report_finding` 过三门后，自动绑该 intent 的原始请求 | 等模型调 `bind_finding_traffic` |
| `capabilities` 的证明级别 | **引擎**：finding 有 PoC+对照组 → 至少 P2 | 模型传参（它传了 P1） |
| `assumptions`（"这条方向不可达"） | **引擎**：intent 标 `stopped/dead` 时自动写一条 | 等模型调 |
| `owned_register`（台账） | **引擎**：检测到立足点（shell 回显/写文件成功）自动登记 | 等模型调 |
| `routes` | **引擎**：从 finding 的 url+param 自动生成 | 等模型调 |

**修法：在这 6 个既有事件点各加一次写库调用（约 200 行），不加工具、不改提示词。**

### B 类：真需要人主动开，不该进主链路（5 个）

`bench_runs`（标尺）、`task_intelligence`（情报）、`skill_usage`（技能）、`finding_cases`（案例整理）、`recheck_state` 的扩展项。

**修法：不删、不改，只在界面上标"需要手动开启"。** 它们不是零基础用户的主路径，硬塞只会again变成噪音。

## 3. 消费端：把已算出来的东西送到人会经过的三个地方

人在一次任务里只会去三处：**会话**（跑着的时候）、**发现**（看结果）、**报告**（交人）。二开的输出要贴这三处，不是另开页面。

| 送什么 | 送到哪 | 数据来源（§2 接通后） | 行数 |
|---|---|---|---|
| 战果两行（能看/能改/能进 + 已拿到什么） | 会话 tab 顶部 | `capabilities` + `assets_owned` | 80 |
| 四行结论（有洞吗/进后台吗/看数据吗/拿权限吗） | 发现 tab 顶部 | `capabilities` 三标签 | 120 |
| 每条洞"能干什么/做不到什么" | 发现 tab 展开 | `capabilities.impact/risk`（字段已存在，没人填） | 100 |
| 白话结论段 | 报告开头 | 同上 | 60 |
| 当前卡在哪 + 该不该继续 | 已有 `TaskErrorBar` 扩展 | `task_error_events`（已分 5 类） | 60 |

**关键：不加新 tab、不加新页面。** 唯一的例外是把「能力菜单」页加一个"从任务详情跳过来（带 taskId）"的链接按钮——它已经有任务选择器，本来就是按任务看的。

## 4. 三档裁决为什么 0 次点击（不要重做它，要挪它）

它现在在「能力菜单」页，而且按钮上写的是**商业决策**（`只拿证据/继续深挖/换目标`）。人不去的两个原因：

1. **位置**：人在任务详情，不在全局能力菜单页。
2. **时机**：它是"每张能力卡"粒度，而人想知道的是"整条路该不该继续"。

**修法（不改它的语义）**：
- 把同一批数据在**任务详情「发现」tab 顶部**渲染一次（四行结论 = 4 张最重要的能力卡）
- 每张卡下面挂原有三档按钮（复用现有接口，不新写决策逻辑）
- 会话 tab 顶部那一行只放**一个**建议 + 一个按钮（最强信号），点击等同裁决

**这样三档裁决从"没人用的功能"变成"人在看结果时顺手点的一下"。**

## 7. 二开的验收标尺：不再用 bench，用"命中率"

`bench_runs` 建了从来没人跑（0 次）。**换一个更便宜的标尺：每次真实任务跑完，自动统计 16 张表的写入情况，低于阈值就报警。**

```
二开命中率看板（任务 #N 结束时自动生成）
  生产端：evidence 12 条 / traffic 绑定 4 条 / assumptions 3 条 / 台账 0 条 ⚠ / routes 2 条
  消费端：四行结论被展开 1 次 / 三档裁决 2 次 / 报告被下载 0 次
  结论：台账仍未接通（目标 >0）
```

**阈值**：A 类 6 个机制每个 ≥1 行；三档裁决 ≥1 次。达不到 = 接线没生效，不许说"优化了"。

这条比 bench 便宜得多，也直接对准这次的问题。

## 附：这份方案和项目自身文档的关系

`docs/01-零基础实战判定.md` 自己的结论是：**"能力层已经很厚（32 个机制 22 个 ✅），但入口太窄、出口没有把关。"**

这次实测补上第三句，也是最重要的一句：

> **生产端根本没写。** 22 个机制里 11 个在这 45 分钟里一行数据都没有——因为它们被做成了"工具"，而模型在真实任务里不调工具，它 bash 了 556 次。

所以二开下一阶段的主题不是"再加机制"，是**"把机制从工具改造成引擎事件上的钩子，把输出从独立页面改造成既有界面的一行"**。
