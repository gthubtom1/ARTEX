## 5. P9 专项：netguard ↔ 前端

**Go 结构**（`internal/netguard/netguard.go:46-53`）：

```go
type Status struct {
    EgressIP   string    `json:"egress_ip"`
    BaselineIP string    `json:"baseline_ip,omitempty"`
    OK         bool      `json:"ok"`
    At         time.Time `json:"at"`
    Detail     string    `json:"detail,omitempty"`
}
```

**实际 API 字段**：

| 来源 | 结构 |
|---|---|
| `GET /api/egress/check`（`quickstart.go:109-112`） | `{exit_ip, baseline_ip, ok, detail}` |
| `GET /api/network.current`（`panel_api.go:84-90`） | `{exit_ip, baseline_ip, ok, detail, at}`（`at` 格式化为 `2006-01-02 15:04:05`） |

| `QuickstartResponse.egress`（`api.ts:1578`） | `{ok, detail?, exit_ip?, baseline_ip?}` |

**前端类型**：

- `EgressCheck`（`api.ts:1583-1589`）：`ok / detail? / exit_ip? / baseline_ip?` —— 与 `/api/egress/check` **一一对应**，但**没有 `at`**（后端也没返回）。
- `NetworkResponse`（`types.ts:1974-1985`）：`settings: Record<string,string>`、`current: {exit_ip?, baseline_ip?, ok?, detail?, at?}`、`egress: {ts,task_id,egress_ip,ok,detail}[]`、`events` —— 与 `GET /api/network` 的 4 个顶层键**完全对应**。

**结论**：`GET /api/network` 本身是对齐的；唯一不一致是 `netguard.Status` 的 JSON tag 写的是 `egress_ip`，而所有对外 API 用的是 `exit_ip`。目前 `Status` 从不被直接 `writeJSON`，所以**没炸**，但这是一个一改就炸的 latent 契约（D5）。

### 6.4 脚本为什么全 PASS 却仍有 bug：15 处盲区

**`audit_links.py`（4 处）**

1. **不校验 HTTP 方法**：`route_set()` 只保留 path（`([^"]+)`），`matches()` 只做 path 正则；把前端 `GET` 改成 `PUT` 仍然 PASS。
2. **只审 `p2api` 之后的 api 对象**：`i = api.find("export const p2api"); block = api[i:]`。`p2api` 定义之前的 `api.*`（例如 `api.setSettings`，`api.ts:936`）完全不在审计范围——而 P9-3 的 bug 正好在 `api/settings`。
3. **只查“路由存在”，不查请求体/响应体/枚举/单位**：`adviser_enabled` 这个字段在两边都不存在，路由 `/api/settings` 却是通的，所以它天然看不见。
4. **页面裸 `fetch` 检查是硬编码名单**：`new_pages = [capabilities, owned, data, ...]`，新增页面不在名单里就永远不会被检查。

**`settings_contract.py`（5 处）**

5. **只 diff `settingsPayload()`，完全不看 `putSettings()` 的请求结构体**：前端声明了、也确实 PUT 了，但后端 struct 没字段，脚本无法发现。
6. **“write-only 豁免”过宽**：凡是出现在 `setSettings({...})` 里的键都被归为 write-only，直接不参与“死字段”判断。`adviser_enabled / verifier_enabled` 正是靠这条豁免过关的。
7. **完全不读 `internal/settings.Defaults`**：31 个默认值（HEAD）里哪些没有读者、哪些与运行时键重名，脚本一无所知。
8. **只审一个 payload**：`/api/environment`、`/api/network` 各自返回 `settings` map，均未与 `Defaults`/前端类型对齐——`work.workers` 与 `net.verify_every_s` 就藏在这里。
9. **不做 key 映射**：`inject_mode` ↔ `inject.mode`、`workers` ↔ `work.workers` 这种 snake↔dotted 关系不在检查范围，也不检查“同一个 setting 两把钥匙”。

**`settings_owners.py`（6 处）**

10. **unmapped 只 WARN 不 FAIL**：`adviser_enabled / verifier_enabled / python_interpreter` 就躺在 warn 列表里，脚本仍 PASS。
11. **字段→setting 的映射靠“位置最近”+驼峰归一，缩写对不上**：`req.PythonInterp` 归一成 `pythoninterp`，前端是 `python_interpreter`→`pythoninterpreter`，于是被误判为“未映射”，从而完全跳过后续 dead/read 检查。
12. **dead 判定只对“已映射”的键生效**：未映射字段永远不会被问“后端到底读没读”。
13. **`ALIASES` 是空表，且不与 `Defaults` 比较**：`workers` vs `work.workers` 这种“同一概念两把钥匙”没有任何机制能发现。
14. **动态读取不可见**：`panel_api.go:52-55` 是 `for _, k := range []string{...} { settings.String(k,"") }`，正则只认字面量 key 和 `settingXxx` 常量，这 13 个键不算“后端读过”；`netguard.BaselineSettingKey` 也不匹配 `settingXxx` 命名。
15. **只查“写冲突”，不查“写→读回路”**：它能发现两个页面覆盖同一个键，但发现不了“按钮写了、GET 不回显、页面读不到”这种单页面闭环断裂（P9-3 的 bug 正是这一类）。

## 8. 每个 bug 的根因与修法

### B1 · adviser/verifier 开关是“假开关”（最严重）

**现象**：点击设置页开关 → toast 提示“已开启” → 开关立刻被 `apply(s)` 改回 false；重启/刷新永远 false。整条 verifier 自动复核链因此永远不会跑（`verifierPass` 第一行就 `return 0`）。

**根因 1**：`server/server.go:3670-3678` 的 PUT 请求结构体没有这两个字段，`encoding/json` 默认忽略未知字段，所以请求 200 但什么都没发生。

```go
InterceptAutoDecide *string `json:"intercept_auto_decide"`
InjectMode          *string `json:"inject_mode"`
...
FindingsVerifyGate  *string `json:"findings_verify_gate"`
}   // ← 没有 AdviserEnabled / VerifierEnabled
```

**根因 2**：`server/server.go:3553-3595` 的 `settingsPayload()` 没有 `adviser_enabled` / `verifier_enabled`，前端 `apply()` 的 `!!s.adviser_enabled` 永远是 `!!undefined === false`。

**根因 3（流程）**：`docs/03-P9强化方案.md:93` 明确把 `server/server.go(payload)` 列进 P9-3 的改动面，但提交 `8c57538` 的 `--stat` 里没有 `server/server.go`。

**修复**：PUT struct 加两个 `*bool` 字段并写 `s.settings.Set(ctx, "adviser.enabled", ...)`；payload 加 `"adviser_enabled": s.settings.Bool("adviser.enabled", false)` 与 verifier 同理；补一条走 `/api/settings` 的回归测试（现有 `llm_role_switch_test.go` 只测 Store，不测 HTTP，所以没兜住）。

### B2 · worker 并发数两把钥匙

```go
// internal/settings/settings.go:22
"work.workers": "3",
// server/manager.go:260
settingWorkers = "workers"
// server/manager.go:317
v, ok, err := m.pg.GetSetting(settingWorkers)
```

`/api/settings` 回显的是 `s.m.Workers()`（读 `workers`），设置页保存也写 `workers`；而 `/api/environment` 回显 `s.settings.String("work.workers","")`（`panel_api.go:53`），该键没有任何写入点，永远取 `Defaults=3`。环境页把 13 个 settings 原样列出（`environment/page.tsx:53`），于是用户把并发改成 8，环境页仍显示 3。

**修复**：`Defaults` 改成 `"workers": "3"`，`panel_api.go` 的键名同步；或让 `Manager.Workers()` 也读 `work.workers`。只保留一个键。

### B3 · 预算占比恒为 0

```go
// agent/p2.go:236-239
in := stall.Input{
    Rounds: rounds, Intents: refs, LayerFacts: layerFacts,
    AssetsInScope: 0, AssetsTested: 0,
}   // ← 没有 Elapsed / Budget
// internal/stall/stall.go:199-201
if in.Budget > 0 {
    rep.BudgetBurnPct = round2(float64(in.Elapsed) / float64(in.Budget) * 100)
}
// agent/p2.go:253
led = adviser.Ledger{Goal: ..., Rounds: ..., IntentCount: ..., NewFacts: ..., Findings: ...} // 也没有 Elapsed/Budget
```

后果：能力卡页永远显示“预算 0%”；`budget_burn` 停顿信号（`stall.go:219`）永远不会进入 `Stuck`，顾问也永远看不到“预算烧了 35%”。

**修复**：从 `Task.FirstRunAt/TimeoutSeconds`（或 `deadline_at`）算出 `Elapsed/Budget` 填进 `stall.Input` 与 `adviser.Ledger`；`0=不限时` 时预算保持 0 即可。

### B4 · 节点 id 被当资产 id 冻结

```go
// agent/p2.go:407（工具入参，且没有 description 说明是节点 id 还是资产 id）
"node_ids": map[string]any{"type": "array", "items": map[string]any{"type": "integer"}},
// agent/p2.go:437
SourceNodeIDs: it.NodeIDs,
// agent/p2.go:1221（读回时直接改名）
it.AssetIDs = nodeIDs
// internal/decision/decision.go:93
v.FreezeAssetIDs = append(v.FreezeAssetIDs, it.AssetIDs...)
```

`source_node_ids` 存的是探索节点 id（`SyncCapabilitiesFromFindings` 里就是 `f.ID`），`add_intent` 的 `anchors` 是资产 id（`agent/tools.go:1142-1151`）。两个 id 空间不同：轻则“换目标”冻结不生效（只写了一句 hint），重则误冻结恰好同号的无关资产。

**修复**：能力卡新增/复用 `asset_ids` 字段并从节点 payload 的 `anchors` 派生；`FreezeAssetIDs` 只接受资产 id。工具入参 `node_ids` 补 description 明确“探索节点 id，不是资产 id”。

### B5 · 台账统计/导出静默截断 200

```go
// internal/ledger/ledger.go:195-197
if limit <= 0 {
    limit = 200
}
// internal/ledger/ledger.go:385
all, err := s.List(ctx, "", 0)
// internal/ledger/ledger.go:393
out["total"] = len(all)
```

`GET /api/owned` 的 `stats.total`、`GET /api/owned/export` 的 `count` 都只覆盖最近 200 条；超过 200 台持有资产时数字开始说谎，且导出文件不完整却没有任何提示。

**修复**：`Stats` 用 `SELECT status, count(*) ... GROUP BY status`；`ExportJSON` 用独立查询（或分页循环）而不是复用 `List` 的默认上限。

### B6 · `net.verify_every_s` 与实现的 60s 不一致

```go
// internal/settings/settings.go:36
"net.verify_every_s": "300",
// server/quickstart.go:108 与 :155
st, err := s.netguard.VerifyCached(r.Context(), 60e9)
```

网络页把这个键当“生效配置”展示（`panel_api.go:71`，`types.ts:1975` 注释也写着它），但真正决定缓存 TTL 的是两处硬编码 60 秒；`internal/netguard/netguard.go:63` 的注释还专门说“让 net.verify_every_s 真正生效”。

**修复**：`egressConfig()` 或调用点改为 `ttl := time.Duration(s.settings.Int("net.verify_every_s", 300)) * time.Second`。

## 9. 设计缺陷的修法（不强行要求本轮改）

- **D1（P9-2 遗留，已修）**：`Defaults` 删掉 4 个代理键（`dc6b24c` 已提交）；但提交信息里“删除 settings: global_proxy / net.proxy_* / net.clash_*”与实际改动（`f95615f` 没碰 `settings.go`）对不上，建议补一条 commit 或在 CHANGELOG 说明。
- **D2（假旋钮）**：`work.max_turns / budget.* / tool.* / kb.search_limit` 要么接上读者（agent 的 max_turns 目前来自 `agents` 表，不是 settings；预算来自任务 `timeout_seconds`），要么从 `Defaults` 删除；留在 `Defaults` 又只在环境页展示，会让人以为“改了有效”。
- **D3（proof_level 默认值）**：统一为“空/非法 → P1（没证据）”，与 `normProof` 的纪律一致；DB 默认值也改 `P1`，或明确保留 `P2` 并在 verify 里对齐。
- **D4（枚举弱约束）**：`capabilities`、`assets_owned` 加 CHECK（`proof_level IN ('P1'..,'D4')`、`confidence IN ('observed','inferred')`、`status IN (...)`）；TS 把 `status/proof_level` 收窄成联合类型，至少 `CapabilityCard`、`OwnedAsset` 两个出口。
- **D5（egress_ip vs exit_ip）**：把 `netguard.Status` 的 tag 改成 `json:"exit_ip"`，或给 `Status` 加 `ToAPI()` 明确转换；同时决定 `EgressCheck` 要不要 `at`（`/api/network` 有，`/api/egress/check` 没有，前端也没用）。
