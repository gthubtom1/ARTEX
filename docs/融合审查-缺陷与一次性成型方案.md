# 融合审查：缺陷、冲突与"一次成型"方案

> 目的：**在写代码前把方案钉死**，避免以后反复返工。
> 审查对象：`docs/` 12 篇设计 × ARTEX 源码（v0.3.18）× `kb/` × `skills/`。
> 结论先行：**方案主体成立，但有 8 处设计冲突、12 处缺失胶水、4 处必须先定的数据模型决策。下面逐条裁决。**

---

## §1 审查结论（三句话）

1. **架构方向对**：在原 planner/worker/双图上加"门 + 图 + 池 + 台账"，不需要换技术栈。
2. **当前方案不能直接开工**：8 处冲突会导致同一个功能两套实现（最典型：`footholds` vs `pivots` vs `assets_owned` 三张表在讲同一件事）。
3. **缺的不是功能，是"胶水"**：开关体系、密钥保管、审计、迁移、幂等、并发锁、测试靶场——这些不补，功能越多越乱。

## §2 八处冲突与裁决

| # | 冲突 | 现状 | 裁决（以此为准） |
|---|---|---|---|
| C1 | `footholds` / `pivots` / `assets_owned` 三张表讲同一件事 | 三篇文档各写一套 | **统一为 `assets_owned`（主）+ `access_refs`（连接方式）+ `routes`（可达）**。`footholds` 并入 `access_refs` |
| C2 | 冻结门 vs 阶段门（都在 `addOneIntent` 拦截） | 两处各加一段 | **合并为 `GateChain`，但只做两件事：① 完全去重（同一意图不重复派）② 优先级排序建议（不拒绝）。代码与文案里不出现任何「禁止/不允许」** |
| C3 | 顾问 agent vs planner（都能"决定下一步"） | 顾问出 hint，planner 派意图 | **顾问永不派意图**（写进代码：工具面不含 `add_intent`）；只允许 `add_hint`/`steer_work`/`kill_work` |
| C4 | 能力卡 vs finding（两条记录链） | 能力卡是菜单，finding 是漏洞 | **能力卡由 finding/fact 派生**，`capabilities` 表带 `source_finding_ids[]`；finding 仍由 `report_finding` 写 |
| C5 | 注入层 vs `agent_prompts`（都在改 system） | 两套机制 | **注入层只追加到 system 末尾**（provider 层）；正文仍走 DB；顺序固定：正文 → 约束 → 意图 → **注入块** |
| C6 | netguard vs `proxyEnv` vs 记录代理（三层都在管出口） | 三处各自注入 env | **固定链路**：netguard.Verify → route resolve → proxyEnv → 记录代理 → 目标。任何一层失败即 fail-closed |
| C7 | `MEMORY.md` vs transcript resume（都做"接着干"） | worker 已能 resume | **分工**：transcript = 同一 intent 的续跑；MEMORY = **跨 worker/跨会话**的交接便条 |
| C8 | 三种授权层（`task.mode` / intercept ask / PermissionMode Bypass） | 互不知道 | **统一策略引擎 `policy/`**：mode 决定"允许到哪一阶段"，intercept 决定"这一步要不要问"，Bypass 仅关掉 SDK 弹窗 |

### 3.2 四条必须先拍板的设计决策

| 决策 | 选项 | **采用** | 理由 |
|---|---|---|---|
| D1 `assets_owned` 是全局还是每任务？ | 每任务 / 全局 | **全局**（主键 `asset_key`），带 `first_task_id` | 你要"10 天后还在"，跨任务必须是同一条 |
| D2 凭据怎么存？ | 明文 / 引用外部 / 加密 | **加密（AES-GCM，密钥文件 0600）+ 只存引用** | 明文口令是最容易出事的地方；报告里也不出现 |
| D3 `capabilities` 与 `exploration_nodes` 什么关系？ | 独立 / 派生 | **派生**（`source_node_ids[]`），finding 变了就重算 | 避免"两套真相" |
| D4 `routes` 与 `pivots` 合并？ | 两张 / 一张 | **一张 `routes`** | 跳板就是路由的来源，没必要两张 |

> **这四条一旦写错，后面所有功能都要改。先定，再写代码。**

## §4 一次命令的完整链路（把它画出来，才知道在哪加钩子）

```
planner 派 intent（带 stage/requires/asset_ids）
   ↓ GateChain：去重 + 优先级排序（不拦截，也不返回「拒绝」）
frontier 队列
   ↓ worker claim
   ↓ policy：mode(recon/attack) 决定允许的工具面
   ↓ PreToolUse：tool_presence（缺工具→装/降级） → risk_tier（高危→需批准/开关）
   ↓ 路由：resolveRoute(target) → routes表 → proxy_endpoint
   ↓ netguard.Verify（出口 IP 校验，失败即停）
   ↓ proxyEnv 注入（HTTP(S)/ALL_PROXY + CA）
   ↓ 记录代理（MITM 留痕）
目标
   ↑ 响应 → traffic_* 可查
   ↑ 写回：insert_assets / record_fact / report_finding（→ 三门校验）
   ↑ 能力卡重算（finding → capabilities）
   ↑ MEMORY.md 追加交接块
   ↑ 图变更 → 唤醒 planner（闭环）
```

**关键**：这条链上每个环节都必须"失败可解释"。现在缺的是 §6 的第 4 项（错误分类）。

## §5 权限策略：默认全开，模型侧零门

### 5.1 核心原则

**不设开关、不做分级、不写任何“禁止”文本。所有能力默认全部可用。**

理由（和你的判断一致）：只要提示词或代码里存在“不允许 X”，模型就可能在无关步骤上误解并拒绝执行——开关开了却还是拒，等于白开。

```
模型看到的：全是“你可以做什么”（正向描述）
模型看不到：任何“你不能做什么”（零负面文案）
代码里的：没有任何权限判断分支（零权限门）
```

### 5.2 唯一保留的两样（都在网络层，模型看不见）

| 保留 | 位置 | 模型能看到吗 | 作用 |
|---|---|---|---|
| **目标清单** | netguard / 路由层（读 `task_scope`） | ❌ 看不到 | 只向清单内的 IP/域名发包；防止误打评分平台或别人的机器导致出局 |
| **出口隧道** | netguard（代理不可用就停） | ❌ 看不到 | 不泄露本机 IP；它不是“限制”，是“管道” |

**关键：这两样不写进提示词、不作为工具报错文案。** 模型只会看到“超时/连不上/失败”，不会看到“你被禁止了”——所以不会触发它自己脑补规则。

### 5.3 原来那些“门”怎么处理

| 原来的门 | 处理 |
|---|---|
| T0–T4 风险分级、feature_flags | **全部删除**。没有开关、没有分级、没有编译期 tag |
| 阶段门（硬拒绝） | 改成**正向排序提示**（“先拿到立足点，再横向”）写进 planner 提示词，**不拒绝任何派单** |
| 冻结门（硬拒绝） | 只保留**完全去重**（同一条意图不重复派）；“没产出”只做**低优先级标记**，不拦 |
| 三门校验 | 保留，改成正向表述：“提交前用三步核实”——产物是事实分类，不是拒绝 |
| recon/attack 模式 | 保留为**任务类型**（你选“先看菜单”），默认 `attack`；recon 只是少派利用类意图，**不拦工具** |

### 5.4 风险靠三样接住（都不打断你）

| 手段 | 形态 | 你会被打断吗 |
|---|---|---|
| **audit_log** | 每步落库（工具/目标/参数摘要/结果） | 不会，后台可查 |
| **出口隧道** | 失败即停 + 明确告警 | 会（任务停并告诉你原因） |
| **台账与复查** | 打下的资产自动入账 + 定期复查 | 不会，页面可看 |
| **自动快照** | 写文件/改配置/删数据前先备份，可一键回滚 | 不会（只有失败回滚时才提示） |

### 5.5 为什么“目标清单”这一根不能去掉

原因很现实，和技术无关：

- 竞赛里流量一旦跑到**评分平台**或别人的机器上，结果不是扣分，是**直接判违规出局**；
- 真实项目里没有授权范围的流量，是刑事风险，不是技术风险。

而它对**你的操作成本为零**：建任务时填目标（或导入一份 txt），之后**范围内零限制**，模型想怎么打就怎么打。

### 5.6 删除开关体系后，ADR 的修正

| 原 ADR | 修正 |
|---|---|
| A2 “所有高危能力只走 feature_flags” | **作废**。改为“高危能力全部默认可用，仅靠审计 + 出口隧道兜底” |
| A4 “三门校验在 report_finding 之前、不可绕过” | 保留，但定性为**质量前置**，不是权限门 |
| A5 “出口链路固定顺序” | **保留并加强**（它是管道，不是门） |

## §6 缺失的胶水（12 项，不补必返工）

| # | 缺什么 | 后果 | 补法 |
|---|---|---|---|
| 1 | **配置中心** | 散落在 env/DB/文件，改一处漏三处 | 统一 `settings` 表 + 启动快照 + 热加载 |
| 2 | **审计** | 出问题无法追溯 | `audit_log`：每步落库，不打断运行 |
| 3 | **密钥保管** | 明文凭据泄露 | `creds_vault`（AES-GCM + 密钥文件 0600） |
| 4 | **错误分类** | 分不清"目标拦/自己错/环境坏" | `errclass`：target_blocked / self_error / env_error / policy_denied |
| 5 | **幂等键** | 重跑产生重复资产/重复 finding | 每写回带 `idem_key`（task+intent+step hash） |
| 6 | **并发锁** | 两个 worker 同时打同一 host | `assets` 行级锁 / 任务级信号量 |
| 7 | **schema 迁移** | 加表靠手改 SQL | 版本化迁移（`schema_version` + 顺序脚本） |
| 8 | **数据保留策略** | 日志/流量无限涨 | 按天归档 + 保留 N 天 + 一键清理 |
| 9 | **本地靶场 fixture** | 没靶子无法验收 | docker-compose 起 DVWA/JuiceShop/VulHub 3 个 |
| 10 | **回归测试** | 改一处崩三处 | 每模块一个验收脚本（§8） |
| 11 | **成本熔断** | token 失控 | `budget` 表 + 到顶即停 + 告警 |
| 12 | **UI 信息架构** | 页面越加越乱 | 先定 8 个页面（任务/菜单/台账/知识/环境/网络/开关/报告） |

## §7 十条"一次成型"决策（ADR）

| # | 决策 | 不这么做的代价 |
|---|---|---|
| A1 | 数据模型**先定后写**（§3 四条） | 后面每加功能都要改表 |
| A2 | **不设权限门**：所有能力默认可用，零负面文案 | 提示词里一旦出现"禁止 X"，模型会在无关步骤误解并拒绝 |
| A3 | 凭据**永不进日志/报告/知识库** | 一次泄露，全部作废 |
| A4 | 三门校验**写进 `report_finding` 之前**，不可绕过 | 报告不可信，等于没有 |
| A5 | 出口链路**固定顺序**（§4） | 出现"某条路径直连"就泄 IP |
| A6 | 全部写回带**幂等键** | 重跑污染图谱 |
| A7 | **能力卡派生自 finding**，不独立维护 | 两套真相必然不一致 |
| A8 | 顾问**无 `add_intent`** | 与 planner 抢职责，绕圈 |
| A9 | `MEMORY.md` 只做**跨 worker 交接** | 与 transcript 重复，浪费 token |
| A10 | 每模块**先写验收脚本再写实现** | 无法判断"做完了没有" |

## §8 验收与回归（每个模块一个可跑脚本）

| 模块 | 验收脚本要证明什么 |
|---|---|
| netguard | 关代理 → 任务拒绝启动；切节点 → 出口 IP 变化且被记录 |
| tool_registry | 卸载 sqlmap → 自动装回或降级，任务不中断 |
| GateChain | 同一意图连派两次 → 第二次被去重合并，模型看不到任何「拒绝」字样 |
| capabilities | 跑一台 → ≥3 卡 + ≥1 负结论，卡里有 evidence |
| triple_gate | 喂一条假 finding（无真实请求）→ 被降级为 inferred |
| footholds | A worker 建的 shell，B worker 能执行命令 |
| creds_vault | 凭据入库后，日志/报告/导出里搜不到明文 |
| assets_owned | 改靶机密码 → 下次复查标 `stale` |
| routes | 经跳板打第二台，出口 IP = 跳板 IP |
| audit_log | 每一步都落库（工具/目标/参数摘要/结果）；模型侧无任何感知 |

**本地靶场**：`docker compose -f fixtures/docker-compose.yml up`（DVWA + Juice Shop + 一个 VulHub 靶机），全部验收在它上面跑。

## §9 风险登记册（按"会不会毁掉项目"排序）

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| token 成本失控 | 高 | 项目跑不动 | 预算熔断 + 多模型分工 |
| 会话/上下文断进度 | 高 | 长任务白跑 | MEMORY 接力 + 实例保活 |
| 幻觉进报告 | 中 | 竞赛扣分/信誉 | 三门校验（不可关） |
| 泄本机 IP | 中 | 真实后果 | netguard fail-closed（不可关） |
| 误操作造成不可逆影响 | 中 | 不可逆 | 不用禁止，用**可回滚**：写前快照、改配置前备份、删前留档 |
| 数据模型返工 | 中 | 拖两周 | §3 先定 |
| 工具缺失卡死 | 高 | 空转 | tool_registry + fallback |
| 时间不够 | 高 | 做不完 | W1–W3 是底线，其余可裁 |

## §10 最终建造顺序（一次成型，不返工）

| 阶段 | 内容 | 为什么在这个位置 |
|---|---|---|
| **P0 地基**（3d） | 数据模型迁移 + settings + audit_log + errclass + 幂等键 | 所有功能的公共依赖，先有再写 |
| **P1 出口与工具**（3d） | netguard + routes + tool_registry + OAST | 保证"能安全跑起来" |
| **P2 编排**（3d） | GateChain（去重+排序）+ task.mode（默认 attack）+ 正向排序提示 | 保证不重复派单、不乱序，且不引入任何拒绝文案 |
| **P3 真相**（3d） | 三门校验 + 声明式提交 + capabilities 派生 | 保证"说的都是真的" |
| **P4 战役**（5d） | access_refs + 凭据收割/复用 + 提权决策 + 横移 | 保证"能打穿一片" |
| **P5 持有**（3d） | assets_owned + 复查计划 + 台账 + MEMORY 接力 | 保证"打下来不丢" |
| **P6 体验**（4d） | 能力菜单 + 决策队列 + 8 个页面 + 报告 | 保证"零基础能用" |
| **P7 优化**（3d） | 多模型分工 + 回放 A/B + 看板 | 锦上添花 |

**总计 ≈ 27 个工作日。**
**顺序不可换**：P0 没做就写 P1，后面每次加功能都要改表（这是最常见的返工原因）。

## §11 一句话

**这套方案现在的状态是"想法齐了、地基没浇"。**
把 §3 的四条数据决策、§5 的三层开关、§6 的十二处胶水先落地，剩下的功能就是"往格子里填"，不会返工。
**反过来，跳过 P0 直接写功能，两周后一定会推倒重来。**
