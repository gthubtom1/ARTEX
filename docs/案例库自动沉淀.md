# 案例库自动沉淀（越用越强的闭环）

> 目标：**每打完一台靶机/一个目标，自动产出一张案例卡**，去重合并，索引自动更新。
> 下次遇到同指纹的站，`kb_search` 直接把"上次是怎么打下来的"给回来——这就是别人下载不到的东西。

---

## 一、触发与取材（全部来自 ARTEX 已有数据）

| 触发点 | 代码位置 | 取什么 |
|---|---|---|
| 任务落 `done` / `timeout` | `server/engine.go` 收尾分支 | 整个任务的方向矩阵 + 全部 finding |
| `report_finding` 落库 | `agent/tools.go` `addFinding`（已有 `notifyFinding` 回调） | 单条漏洞的完整证据 |
| worker 结束 | `server/engine.go` `runIntent` | 该意图的 trace（每步命令 + 关键输出） |

**不用新增埋点**——`exploration_nodes` / `activity` / `traffic` / `finding` 四张表已经齐了。

## 二、案例卡的字段映射

| 案例卡字段 | 来源 |
|---|---|
| `dedupe_key` | `指纹 + 手法 + 面形状 + payload 类`（见 §3） |
| `目标画像.指纹` | 该任务里 `assets.type='app'` 的 tech/version 属性 |
| `目标画像.暴露面` | 首个成功 finding 锚定的 `endpoint` |
| `成功路径` | 该 finding 的 `derived_from` 血缘链上所有 intent 的 summary，按时间排序 |
| `关键 payload` | finding.evidence 里的请求行 + payload 段（自动抽取，抽不到就让 reporter 补） |
| `失败过的尝试` | 同方向 `state in (blocked, exhausted)` 的意图 + trace 里的报错行 |
| `耗时与成本` | intent 的 `started_at/ended_at` + LLM 调用数 |
| `复用条件 / 反例` | 由 `reporter` agent 生成（它已经在写报告，顺手多写两段） |

## 三、去重（这是"不能无限重复"的答案）

```
dedupe_key = normalize(指纹) | tactic | method + path_pattern | payload_class
例：thinkphp-5.0.23|rce|GET /index.php?s=captcha|_method=__construct
```

| 情况 | 动作 |
|---|---|
| key 完全相同 | **不新增文件**：`success_count + 1`、`last_seen` 更新、新 payload 变体追加进 `variants[]` |
| key 不同，指纹+手法相同 | 允许并存（不同面形状是不同经验），互相写进 `related` |
| 内容近似（3-gram Jaccard ≥ 0.90） | `kb_index.py` 标 `near_duplicate_of`，人工确认后合并 |
| 同一目标重复跑 | 合并，`success_count` 递增；**不产生新卡** |

合并优于新增：**同一件事只有一份正文**，靠计数字段体现"这条经验被验证过多少次"。

## 四、写入路径（两种，任选）

### A. 零代码（推荐先做）
自定义工具 `kb_case_save`（`kind=script`，指向 `kb/scripts/kb_case_save.py`）：

```json
// 入参
{"dedupe_key":"...","fingerprint":"...","tactic":"rce","surface":"...","payload":"...",
 "path":["intent1","intent2"],"failures":[{"try":"...","why":"..."}],
 "success_count_delta":1,"target":"TARGET"}
```
脚本负责：找已有卡 → 有则合并（改 frontmatter 的 `success_count/last_seen/variants`）→ 无则新建 → 调 `kb_index.py`。
**不写 Go，不改引擎**，挂在 worker/reporter 上即可。

### B. 引擎内置（P2 再做）
`server/engine.go` 收尾时调用 `kb.SaveCase(...)`，同仓库内直接写文件。好处是不依赖 agent 记得调用；坏处要改 Go。

## 五、脱敏（硬规则，写进脚本）

| 内容 | 处理 |
|---|---|
| 目标 IP/域名 | 一律替换成 `TARGET` / `10.10.10.5` |
| 凭据/Token/Cookie | 只保留"类型 + 长度"，原文丢弃 |
| 客户名/内网域名 | 丢弃 |
| 真实人名/邮箱 | 丢弃 |

案例卡是**经验**，不是**情报**。带原文的卡一律不进 `cases/`。

## 六、索引更新（自动化）

```bash
# 每次写入后（脚本内部调用）
python kb/scripts/kb_index.py

# 定时兜底（crontab / Windows 计划任务 / ARTEX 的「计划任务」功能）
python kb/scripts/kb_index.py --check || python kb/scripts/kb_index.py
```

`--check` 在索引过期时返回 1，可以拿去告警；`--strict` 在有重复时返回 1（CI 用）。

## 七、闭环效果（怎么证明它"越用越强"）

| 阶段 | 指标 | 观测方式 |
|---|---|---|
| 第 1 周 | cases 数量 0 → 5 | `index.json` 的 `count` |
| 第 2 周 | 新任务里 `kb_search` 命中旧 case 的次数 > 0 | `refusal_events` 旁边的 `kb_hits` 统计（建议同表记一条） |
| 第 4 周 | 同指纹任务的「首次成功耗时」下降 | 案例卡的 `time_to_root` 对比 |
| 长期 | 重复卡比例 < 10% | `kb_index.py` 的 `problems` |

**如果 4 周后 cases 增长但「首次成功耗时」没降，说明卡写得不合格**（缺复用条件或 payload 抽取失败），回去修模板，不要继续堆数量。

## 八、与顾问 agent 的联动

顾问在出"换层建议"时，**必须先 `kb_search` 一次**该指纹：

- 有命中案例 → 直接给"上次这条链是怎么打的"，而不是让 worker 从零试
- 无命中 → 这是**真空区**，优先级应高于重复深挖（记一条 `fact`：该指纹无既有经验）

这一条把"经验"和"纠偏"接上了：**顾问的建议不再来自模型臆想，而来自你自己的历史。**
