# 21 · 效果验收（"完成"的最终定义）

> 起因：用户质问——「不要用代码没问题当完成。最终它到底有没有效果？」
> 本文把"效果"写成可测的数字，并给出当前实测值。**代码完成 ≠ 有效**，这份文件就是两者的分界线。

---

## 二、`完成` 的效果定义（5 条硬指标，缺一不算）

| # | 指标 | 判据（怎么量） | 现状 |
|---|---|---|---|
| **F1 能拿到权限** | 在至少 1 个标准靶场上用 ③ 模板跑完，**到 E3（命令执行）或 E4（数据样本）**，并把证据写进台账/事实 | `assets_owned ≥1` 或 `chain.status=done` 且 `steps.gain:shell/data` 存在 | ❌ 0 次 |
| **F2 误报可控** | 报出的漏洞人工抽样验证，**误报率 ≤ 10%**（抽查 10 条至少 9 条成立） | 人工标注表 + `findinggate` 统计 | ❌ 未做（只有 2 条样本） |
| **F3 可复现** | 同一靶场连跑 3 次，等级/漏洞数波动可解释（不是随机） | 3 次记录对比 | ❌ 未做 |
| **F4 成本可见** | 每个 finding 的 token 成本有账，单任务时长在模板设定内 | `llm_usage` 按 task 聚合 | ⚠ 有账（60M/2），但成本畸高 |
| **F5 零基础可走通** | 贴网址 → 选模板 → 拿到结论卡 + 报告，全程不需要命令行 | 录屏/界面截图 + 无 CLI 参与 | ⚠ 设计齐，未做真人验收 |

## 三、差距清单（按"影响效果"排序）

| 优先级 | 缺什么 | 为什么影响效果 |
|---|---|---|
| P0 | **没有标准靶场基准跑分** | 现在只有 2 个真实站的经验值；没有对照，无法回答"到底强不强"。`internal/bench` + `bench/cases` 代码在，**从未跑过** |
| P0 | **"漏洞→利用"这一步没有被强制** | 链只到"确认+授权"，AI 拿到授权后没有再往前推（要么它想不到、要么它懒）。需要在链上做"未完成就催"的闭环（已有一半：审查官催，但没有硬门） |
| P1 | **权限等级靠文本关键词判定** | E3/E4 是拿 vulnclass/evidence 里的词匹配出来的，会漏（真正的证据是请求/响应原文）。应改为"证据可解析"：能重放请求/能拿到输出才算 |
| P1 | **成本畸高** | 60M token / 2 漏洞。planner 每 20-60 秒重规划一次，大量重复上下文。需要按"每步收益"节流 |
| P2 | **误报率未知** | 三门校验在，但没有统计。F2 量不出来，用户就不敢信报告 |
| P2 | **单目标深挖没有"下一步一键执行"** | 点了允许之后，还要等 agent 自己想起来。应该在点允许时直接下发一条意图（现在是靠它自己规划） |
| P3 | 五个条件机制（持有台账/复查/路由/流量绑定/案例） | 需要立足点/≥2 漏洞才有数据；F1 不到就永远为 0 |

## 四、验收流程（可重复执行）

```bash
# 1) 起靶场（3 个，任选其一可跑；有 docker 的机器）
docker compose -f bench/compose.yml up -d        # DVWA :18081 / DSVW :18083 / juice-shop :18084

# 2) 每个靶场跑 ③ 模板（40 分钟），记录
#    - 漏洞数 / 是否到 E3 / 是否到 E4 / 报告是否可交付 / token 成本 / 耗时

# 3) 逐条人工核对漏洞真实性（F2）
#    在 ./evidence/bench-<date>.md 里写：findings、抽检结论、误报数

# 4) 连跑 3 次同靶场（F3），比较等级与漏洞数
```

**F1 的自动判据（跑完直接查）**：
```sql
-- 是否拿到命令执行
select count(*) from exploration_nodes n join tasks t on t.exploration_id=n.exploration_id
 where t.id=<ID> and n.kind='finding'
   and (coalesce(n.payload->>'vulnclass','') ~* '(rce|命令执行|代码执行|webshell)');
-- 是否登记立足点
select count(*) from assets_owned where first_task_id=<ID>;
-- 链是否走完
select chain_key,status from chains where task_id=<ID>;
```

## 五、什么时候可以说"彻底完成"

**F1 至少 1 次通过 + F2 误报率 ≤10% + F3 跑满 3 次** 之后，才能对用户说"这个工作台真的能拿权限"。
在那之前，只能说"链路完整、设计合理、还没被证明有效"。
