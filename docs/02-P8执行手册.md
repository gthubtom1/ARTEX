### P8-1 内置基准跑分（2d）

#### 为什么

现在 24 份文档里所有"更强/更快"的判断都没有标尺，导致每轮都在重新争论"到底有没有变好"。
跑批结果一旦落盘，**后面 8 条改动全部可以量化**。

#### 现状

- 只有零星的手工实测：DSVW 单靶场，flash 模型，52–82s 出首个 finding。
- 没有任何"同条件重复跑 + 通过率"的数据。
- `fixtures/docker-compose.yml` 里已有 DVWA / Juice Shop / VulHub，但只是"能起来"，没有打分。

#### 设计

**用例 = 一道题**，定义在 YAML：

```yaml
# bench/cases/sqli-01.yaml
key: sqli-01
name: 布尔盲注读数据
category: sqli                 # sqli|cmdi|path-traversal|upload|deser|ssrf|idor|auth-bypass|ssti|weak-pass
url: http://127.0.0.1:18081/login.php
goal: 目标 {url}，读出数据库里 users 表的第一行用户名与口令哈希；只测这个地址。
timeout_s: 300
pass:
  # 判定方式（满足任一即可）
  finding_vulnclass: ["sql-injection", "sqli"]
  finding_surface_regex: "/login\\.php"
  finding_evidence_regex: "(union\\s+select|sleep\\(|and\\s+1=1)"
```

**判定原则**：用**平台自己报出的 finding** 判定，而不是外部探针 —— 我们在测"平台能不能打穿并证明"，不是测"漏洞存不存在"。

**跑批器**（`scripts/bench/run.py`，Python，约 250 行）：

```
读取 bench/cases/*.yaml（或 --set 指定的子集）
对每个用例：
  1. POST /api/tasks   {description, goal, timeout_seconds, seed_first_intent:true, llm_profile_id:<指定>}
  2. 轮询 GET /api/tasks/{id} 直到 done/timeout/failed，最长 timeout_s+60
  3. GET /api/tasks/{id}/findings 拉 findings
  4. 按 pass 规则判定 passed
  5. 记录：duration_ms / 首个 finding 耗时 / token（GET /api/replay/compare 或任务详情里的 token 字段）
串行执行（默认 -p 1），因为平台本身有并发上限，并行会互相干扰
写出 bench/results/<run_key>.json，并 POST /api/bench/ingest 让后端登记到 bench_runs
清理：--cleanup=true 时删除本次创建的任务（默认保留，便于人工看）
```

**后端（新增 `server/bench_api.go`，约 150 行）**

```go
func (s *Server) registerBenchRoutes(mux *http.ServeMux) {
    mux.HandleFunc("POST /api/bench/ingest", s.benchIngest)   // 幂等 UPSERT 到 bench_runs
    mux.HandleFunc("GET  /api/bench/runs",   s.benchListRuns) // 列表（含环比）
    mux.HandleFunc("GET  /api/bench/run",    s.benchGetRun)   // 读 results/<run_key>.json 返回明细
}
```

- `benchIngest`：只接受 `run_key` / `set_name` / `model_profile` / `total` / `passed` / `duration_ms` / `total_tokens` / `notes`，`ON CONFLICT (run_key) DO UPDATE`。
- `benchListRuns`：`SELECT ... ORDER BY created_at DESC LIMIT 50`，并算 `pass_rate`、与上一条同 `set_name+model_profile` 的 `delta`。
- `benchGetRun`：**路径穿越防护**（只允许 `^[A-Za-z0-9._-]+\.json$`），从 `bench/results/` 读文件。

**前端（`/system/bench`）**

- 顶部：最近一次运行的大字（`4/10 通过 · 41.2% · 平均 183s/题`）+ 与上次的 `delta`（带箭头与颜色）。
- 表格：题号 / 类别 / 通过 / 耗时 / 首个 finding / token / 任务链接。
- 右下角：`复制跑批命令`（`python scripts/bench/run.py --set basic --profile <id>`）。
- 导航注册：`{ id: "bench", title: "基准", url: "/system/bench", icon: Gauge }`。

### P8-3 三门校验接进 `report_finding`（1d）

#### 为什么

现在 `report_finding` 完全不调 `internal/verify` —— 幻觉条目（只有版本号、只有状态码、只有"看起来可注入"）能直接入库、直接进报告。
这是"可信"这件事上**唯一**能甩开上游和其他开源产品的硬差异点，而且代码已经在仓库里，只是没接上。

#### 现状（代码事实）

- `internal/verify/verify.go:49` `Check(Claim, Options) Verdict`，输出 `Level ∈ verified|inferred|rejected` + `ProofLevel` + `Gates` + `Reasons`。
- 调用点只有两处：`agent/p2.go:425`（`record_capability`）、`agent/p2.go:593`（`verify_claim` 工具）。
- `agent/tools.go:1292 addFinding` → `t.findingRecorder.Record(ctx, input, refs)`，**中间没有任何校验**。

#### 设计

加一个**质量闸**（不是权限闸），三档可配：

`findings.verify_gate` = `off` | `infer`（默认） | `strict`

| 档 | rejected 的行为 | inferred 的行为 |
|---|---|---|
| off | 照旧入库 | 照旧入库 |
| infer | **不入库成 finding**，改写成 `record_fact(confidence=inferred)`，并把理由返回给模型 | 入库，但 summary 前缀 `【未独立复现】`，evidence 末尾追加 `[gate:inferred]` |
| strict | 同 infer | 也不入库，退回让模型补证据 |

**`Options` 的自动推导**（不要靠模型自己填，能算的都算）：

| 字段 | 来源 |
|---|---|
| `ToolVerified` | `evidence` 里命中 `nuclei` / `oast` / `callback` / `dnslog` / `interactsh` 任一 |
| `Independent` | 该 finding 已有 `reproduced` 结论的 retest（查 `finding_retests`），或 evidence 里出现 ≥2 个不同的 HTTP 方法/路径 |
| `ControlTested` / `ControlNote` | 新增可选入参 `control_tested: bool`、`control_note: string`；模型不填就是 false |
| `RetestOK` | 同 `Independent` |

#### 改动清单

| 文件 | 动作 |
|---|---|
| `internal/settings/settings.go` | 加 `"findings.verify_gate": "infer"` |
| `agent/tools.go` | `addFinding` 的 handler 在 `Record` 之前插入校验分支（约 40 行）；schema 加 `control_tested` / `control_note` 两个可选参数 |
| `agent/tools.go` | 抽一个 `func (t *ToolSet) findingGate(a *findingArgs) (verify.Verdict, bool)` 便于单测 |
| `server/server.go` | `settingsPayload` / `putSettings` 暴露 `findings_verify_gate` |
| `agent/finding_gate_test.go` | 新文件：off/infer/strict × verified/inferred/rejected 六种组合 |
| 前端 | 不强制加页面；放到「系统 → Agent」或「系统 → 拦截规则」里一个单选即可（可选） |

#### 关键代码骨架

```go
// agent/tools.go，在构造 input 之后、Record 之前
gate := findingVerifyGate() // 从 settings 读，off 时直接跳过
if gate != "off" {
    v := verify.Check(
        verify.Claim{Title: a.Name, Surface: a.VulnClass, Evidence: a.Evidence, ProofLevel: ""},
        verify.Options{
            ControlTested: a.ControlTested,
            ControlNote:   a.ControlNote,
            ToolVerified:  evidenceHasToolMark(a.Evidence),
            Independent:   t.hasReproducedRetest(pid(a.IntentID), a.Name),
            RetestOK:      t.hasReproducedRetest(pid(a.IntentID), a.Name),
        },
    )
    switch v.Level {
    case "rejected":
        // 不入 finding，改记一条待验证事实
        _, _ = t.recordFactForGate(ctx, a, v.Reasons)
        return actool.Textf("证据不足，已记为待验证（inferred）：%s。补齐请求/响应原文或独立复现后可重新上报。",
            strings.Join(v.Reasons, "；")), nil
    case "inferred":
        if gate == "strict" {
            return actool.Textf("证据只能判到 inferred（%s），严格模式下不入库。请补一次独立复现。",
                strings.Join(v.Reasons, "；")), nil
        }
        a.Summary = "【未独立复现】" + a.Summary
        a.Evidence = a.Evidence + "\n\n[gate:inferred] " + strings.Join(v.Reasons, "；")
    }
}
```

#### 坑

1. **`record_fact` 的调用方式**：`ToolSet` 里已有 `recordFact` 的内部实现，但它是工具函数。抽一个 `recordFactInner(ctx, input)` 复用，不要复制逻辑。
2. **别阻断 retester/verifier**：它们写的是 `finding_retests` / `evidence_timeline`，不走 `addFinding`，不受影响。
3. **`planner` 也能调 `report_finding`**：闸对 planner 同样生效（这是好事）。
4. **老数据**：默认 `infer` 上线后，之前已存在的 finding 不动；只在报告里加一行说明"闸开启时间"。

#### 验收判据

1. 构造一条只有版本号的 finding（`evidence` = "ThinkPHP 5.0.23 存在 CVE-2018-20062"）：`infer` 档必须被拒，返回文案含"证据不足"，且库里出现一条 `inferred` 的 fact 而不是 finding。
2. 构造一条带完整请求/响应 + 对照组 + 独立复现的 finding：必须入库且 summary **没有** `【未独立复现】` 前缀。
3. `findings.verify_gate=off` 时行为与改动前一致（跑现有的 `finding_workflow_test.go` 全绿）。
4. 报告 `GET /api/report` 里，`inferred` 的条目要能与 confirmed 区分（已有 `confidence` 字段，确认它在报告渲染里被读出来）。

### P8-5 台账状态机 + 决策冻结消费者（0.5d）

#### 为什么

- 现在 `assets_owned` **一次复查失败就 `stale`**，`lost` 只能手动设 —— 文档写的"连续 3 次→lost"没实现，台账会长期挂一堆假 stale。
- 用户点"换目标"（决策 `switch`），`decision.Verdict.FreezeAssetIDs` 算出来了，但**没有任何消费者**，等于只写了一句 hint。用户会以为按钮没生效。

- `internal/ledger/ledger.go:256 RecordCheck`：`!ok` → 直接 `status="stale"`。
- `internal/ledger/ledger.go:59 staleAfter` 算了但 DB 分支没用。
- `internal/decision/decision.go:45/93` `FreezeAssetIDs` 只出现在计算与测试里。

#### 设计

**A. 台账状态机（严格按表实现）**

| 当前 | 事件 | 新状态 | 附action |
|---|---|---|---|

| stale | 复查 ok | verified | `fails=0` |

### P8-6 netguard 覆盖 Bash / WebFetch（0.5d）

#### 为什么

现在 `netguard` 只拦 `execx` / `remote` / `recheck` / `replay` / adapter。
**worker 最核心的 `Bash` 完全不受它管** —— 模型一句 `curl --noproxy '*' http://target` 就绕过整个出口体系。
而"不泄露本机 IP"是这个项目的底线之一。

#### 现状（代码事实）

- `internal/egress/egress.go:14 Guard()`：未注入 `Check` 时返回 nil（fail-open 空实现）。
- `agent/worker.go:460 BashEnv: proxyEnv(...)`：只注入 env，不校验。
- `guard/guard.go:96 preToolUse`：只做审计 + `ToolPresence` + `applyIntercept`，**无出口校验**。
- `net.verify_every_s`（默认 300）**全仓无读取点** → 每次 `Verify` 都真发两次外网请求。

#### 设计

**A. `net.verify_every_s` 真正生效**

`internal/netguard` 加一个结果缓存：

```go
type cacheEntry struct { at time.Time; info Info; err error }

func (g *Guard) VerifyCached(ctx context.Context, ttl time.Duration) (Info, error) {
    g.mu.Lock()
    if e := g.cache; e != nil && time.Since(e.at) < ttl {
        g.mu.Unlock()
        return e.info, e.err
    }
    g.mu.Unlock()
    info, err := g.Verify(ctx)
    g.mu.Lock(); g.cache = &cacheEntry{time.Now(), info, err}; g.mu.Unlock()
    return info, err
}
```

- 失败结果也缓存（但 TTL 取 min(ttl, 30s)），否则代理挂了会每轮打两次外网。

**B. Bash / WebFetch 前置闸**

`guard` 加包级注入点（照 `ToolPresence` 的写法）：

```go
// EgressCheck 由 server 注入；返回 error 即拒绝执行。
var EgressCheck func(context.Context) error
// EgressToolFilter 判断这条命令是否"要发网络包"；nil 时用内置词表。
var EgressToolFilter func(tool, cmd string) bool
```

在 `preToolUse` 里，`applyIntercept` 之前插入：

```go
if EgressCheck != nil && egressIntent(ev.ToolName, cmd) {
    if err := EgressCheck(ctx); err != nil {
        errev.Emit(ctx, taskIDFromCtx(ctx), "env_error", ev.ToolName, err.Error())
        return g.block(ev.ToolName,
            "出口未就绪："+err.Error()+"。请起代理或到「系统 → 网络」改代理；只打本地靶场可在启动时设 ARTEX_ALLOW_DIRECT=1。", cmd)
    }
}
```

内置网络意图词表（`egressIntent`）：

```
工具名 ∈ {WebFetch} → true
工具名 ∈ {Bash, shell_open, shell_send} → 命令首个词 ∈ {
  curl,wget,nc,ncat,socat,ssh,scp,sftp,ftp,mysql,psql,redis-cli,mssql-cli,
  nmap,masscan,ffuf,gobuster,feroxbuster,nuclei,httpx,subfinder,amass,dig,host,nslookup,
  ping,traceroute,openssl,sqlmap,hydra,netexec,smbclient,impacket-*,psexec.py,
  git,pip,pip3,go,npm,python,python3,node
}
或命令里出现 ` http://` / ` https://`
```

> 保守起见：`python`/`node`/`git` 也在表里 —— 它们都能发网络请求。代价是出口没通时这些命令会被拦；这是**期望行为**（比悄悄泄露 IP 好）。

**C. 前端**

`/system/network` 加一块"最近 1 小时被拦下的网络调用"（读 `task_error_events where class='env_error' and tool in ('Bash','WebFetch')`）。

#### 改动清单

| 文件 | 动作 |
|---|---|
| `internal/netguard/netguard.go` | 加 `VerifyCached` + 缓存字段；`net.verify_every_s` 真正读 |
| `guard/guard.go` | 加 `EgressCheck` / `EgressToolFilter` 注入点 + `egressIntent` + 拦截分支 |
| `server/server.go` `wireP0` | `guard.EgressCheck = func(ctx) error { _, err := s.netguard.VerifyCached(ctx, ttl); return err }`；`ARTEX_ALLOW_DIRECT=1` 时置 nil |
| `guard/egress_test.go` | 新文件：curl 被拦 / `ls` 不被拦 / ALLOW_DIRECT 不拦 |
| `web/.../system/network/page.tsx` | 加"被拦记录"表格 |

#### 坑

1. **不要把 `ARTEX_ALLOW_DIRECT=1` 时也拦** —— 本地靶场模式必须能直连。
2. **`block` 文案必须是环境语气**（"出口未就绪"），不是"禁止"。模型看到"禁止"会开始脑补规则（D01）。
3. **`python -c "print(1)"` 也会被拦** —— 可接受，但要在文案里给"如果是纯本地计算，改走 Write/Read 工具"的提示。
4. 缓存失败结果时 TTL 要短，否则代理恢复后要等 5 分钟才放行。

#### 验收判据

1. `ARTEX_ALLOW_DIRECT` 未开 + 代理不可用 → worker 执行 `curl http://example.com` 被拦，返回文案含"出口未就绪"，且 `task_error_events` 多一条 `env_error`。
2. 同条件下执行 `ls -la` **不被拦**。
3. `ARTEX_ALLOW_DIRECT=1` 时上述 `curl` 不被拦（本地靶场模式）。
4. 连续 10 次 `Verify` 在 300s 内只发 ≤2 次外网请求（看代理日志或加计数断言）。

### P8-7 凭据 key 与首启向导（0.5d）

#### 为什么

`ARTEX_CRED_KEY` 为空时，`agent.NewP2` 静默换成随机的 ephemeral key（只在启动日志打一行 `cred_key_set=false`）。
后果：**重启后所有已存的凭据都解不开，而且没有任何提示**。用户会以为"凭据丢了/平台坏了"。

#### 现状（代码事实）

- `agent/p2.go:41-46`：`creds.NewVault(credKey)` 失败 → `NewEphemeralVault()`，无告警。
- `internal/creds/creds.go:36 NewVault`：空 key 返回 error。

#### 设计

**A. 密钥文件兜底（推荐，比改 config.json 安全）**

新建 `internal/creds/keyfile.go`：

```go
// LoadOrCreateKey 优先用环境变量；为空时读 <dataDir>/cred.key；
// 文件不存在则生成 32 字节随机 hex 并以 0600 写入。
func LoadOrCreateKey(dataDir string) (string, error)
```

- 返回 `(keyHex, nil)` 时把**指纹**（`sha256(key)[:8]`）存到 P2，供页面显示。
- 目录不可写时返回 error，由 `NewP2` 打**显式告警日志**并降级 ephemeral（保留原行为，但不再静默）。

接入点：`cmd/artex/main.go` 在 `server.New` 前：

```go
if os.Getenv("ARTEX_CRED_KEY") == "" {
    if k, err := creds.LoadOrCreateKey(*dataDir); err == nil {
        os.Setenv("ARTEX_CRED_KEY", k)   // 让已有的 NewP2 路径直接复用
        log.Printf("[creds] 已使用 %s/cred.key 作为凭据主密钥（指纹 %s）", *dataDir, fp)
    } else {
        log.Printf("[creds] 警告：无法创建密钥文件（%v），凭据库将使用临时密钥，重启后旧密文不可解", err)
    }
}
```

> 用 `os.Setenv` 是最小改动：`agent.NewP2(m.pg, os.Getenv("ARTEX_CRED_KEY"))` 不用改。

**B. 首启向导 `/system/onboard`**

四步，每步可跳过，每步都写 settings 并给"跳过后会怎样"：

| 步 | 内容 | 跳过后果 |
|---|---|---|
| 1 数据库 | 显示当前 DSN 是否连通（`GET /api/health/db`） | 进程都起不来，实际上跳不过 |
| 2 模型 | provider / model / api_key / base_url + "测一下" 按钮；给档位提示 | 任务排队永不启动 |

| 4 凭据 | 显示"凭据加密：已启用（指纹 xxxx）"或警告 | 重启丢凭据 |

- 侧边栏注册 `{ id: "onboard", title: "首次配置", url: "/system/onboard", icon: Rocket }`（放在「系统」组末尾）。

| 文件 | 动作 |

1. **Windows 上 0600 不生效**：`os.Chmod` 在 Windows 是 no-op。要额外用 `syscall` 设置 ACL 太重 —— 折中：文件放在 `data/`（用户目录下），并在日志里说明"Windows 下目录权限由用户 profile 保证"。
2. **不要覆盖已有 key**：文件存在就复用，绝不重新生成（否则旧密文全废）。
3. **`os.Setenv` 的副作用**：子进程（Bash）会继承这个 env，凭据主密钥会暴露在工具进程环境里。**必须**在 `proxyEnv` / `BashEnv` 构造时过滤掉 `ARTEX_CRED_KEY`。这是一条新发现的泄露面，必须一起做。

#### 验收判据

1. 删掉 `data/cred.key` 和 `ARTEX_CRED_KEY`，启动 → 日志出现"已使用 …/cred.key"，文件存在且内容 64 位 hex。
2. 加一条凭据 → 重启 → 仍能解出（`cred_list` 可读）。
3. `echo $ARTEX_CRED_KEY` 在 worker 的 `Bash` 里为空（env 过滤生效）。
4. 向导四步全程不跳设置页，也能跑起一个本地靶场任务。

### P8-8 错误可解释面板（1d）

#### 为什么

零基础用户最常问的不是"这个洞怎么打"，而是"它为什么不动了"。
现在错误散在活动流、审计、工具输出里，而且模型看到的是"超时/失败"，用户看到的是空白。

#### 设计

**分组规则（固定 5 类，不要更多）**

| class | 判定 | 人话 |
|---|---|---|
| `env_error` | 代理不通 / DNS 失败 / `connection refused` / `command not found` 之外的执行环境问题 | 环境（代理/网络/DNS） |
| `tool_missing` | 命令首词不存在 | 缺工具 |
| `target_blocked` | 目标返回 401/403/429/503、WAF 页 | 目标拒绝 |
| `self_error` | 本机代码异常 / LLM 调用失败 / 解析失败 | 平台自己出错 |
| `policy_blocked` | 拦截规则 / 出口闸 / 决策冻结拦下 | 被规则拦下 |

**接口 `GET /api/tasks/{id}/errors?window_min=60`**

```json
{
  "total": 12,
  "groups": [
    {"class":"env_error","count":5,"sample":"proxyconnect tcp: dial tcp 127.0.0.1:7897: connect: connection refused",
     "action":"起代理或到「系统 → 网络」改代理","fix":"open:/system/network"},
    {"class":"target_blocked","count":4,"sample":"HTTP 403 from /admin","action":"目标有 WAF，先做只读指纹（已有能力）","fix":"open:/function/capabilities"}
  ]
}
```

**前端**

`web/src/app/(main)/function/tasks/detail/` 顶部（活动流之上）加一行：

```
当前卡在：环境（代理连不上）×5 ｜ 目标拒绝（403）×4 ｜ 缺工具（sqlmap）×1      [展开] [一键修]
```

点类别 → 展开该类的最近 20 条原始记录 + 对应 `task_error_events` 的时间戳。
"一键修"：`env_error` → 跳 `/system/network`；`tool_missing` → 跳 `/system/environment` 并预填工具名；`target_blocked` → 跳能力菜单。

#### 改动清单

| 文件 | 动作 |
|---|---|
| `db/migrations/0004_p8.sql` | `task_error_events`（已在 P8-0-A） |
| `internal/errev` | P8-0-B |
| `server/errors_api.go` | 新文件：聚合查询 + 分类建议映射 |
| `server/errors_api_test.go` | 新文件：5 类各一条 → 分组正确 |
| `web/.../tasks/detail/` | 顶部聚合条组件 |
| `web/src/lib/api.ts` | `p2api.taskErrors` |

#### 坑

1. **聚合要在 SQL 里做**（`GROUP BY class`），不要拉全部行到 Go 里再统计。
2. **sample 要截断**到 200 字符，否则长报错把 UI 撑爆。
3. **别把 `policy_blocked` 包装成"禁止"** —— 文案写"被规则拦下（可在「拦截规则」里改）"。

#### 验收判据

1. 拔掉代理跑任务 → 任务详情顶部出现"环境（代理连不上）×N"，点"一键修"跳到网络页。
2. 卸掉 sqlmap 再让 worker 跑 sqlmap → 出现"缺工具（sqlmap）×1"。
3. 目标返回 403 → 出现"目标拒绝（403）×N"。
4. 5 类都不出现时，该组件不渲染（不占位置）。

### P8-9 模型分层引导（0.5d）

#### 为什么

per-agent 绑定（`agentKey` = goals/planner/worker/mainagent/adviser/verifier/retester）**已经实现了**，
但建任务时没有任何引导，用户默认全用同一个模型。结果：planner 用便宜模型 → 规划质量差 → 看起来"平台不行"。

#### 设计

**A. 三档预设（settings）**

```json
{
  "llm.tier.planner": "<profile_id 或空>",
  "llm.tier.worker":  "<profile_id 或空>",
  "llm.tier.verifier":"<profile_id 或空>"
}
```

留空 = 跟随全局激活配置（现状）。

**B. 建任务时给建议**

`GET /api/llm/tier-suggest` → 根据已配置的 profile 列表给出建议：

```json
{
  "suggest": {"planner": 2, "worker": 4, "verifier": 3},
  "reason": "planner 建议用能力最强的一档（决策质量决定全局）；worker 可用便宜档（调用量最大）；verifier 用中档（只判证据）。",
  "profiles": [{"id":2,"model":"claude-opus-4.5","tier":"high"}, ...]
}
```

档位判定用模型名的关键词表（`internal/llmmodel/tier.go`，纯函数）：

```
high:   opus, gpt-5, o3, o4, gemini-3-pro, sonnet-4.5
mid:    sonnet, gpt-4.1, qwen-max, glm-4.6, deepseek-v3.2
low:    flash, mini, lite, turbo, haiku, 8b/7b/4b
```

**C. UI**

`QuickStartCard` 加一行（默认折叠）：`模型：planner=高 / worker=便宜 / verifier=中（推荐 · 改）`。
点"改"弹三档下拉，写 `llm.tier.*`。

#### 改动清单

| 文件 | 动作 |
|---|---|
| `internal/llmmodel/tier.go` + `_test.go` | 新文件：模型名 → high/mid/low |
| `server/llm_tier_api.go` | `GET /api/llm/tier-suggest`、`PUT /api/llm/tier` |
| `server/task_llm.go` | 解析 `taskLLMRuntime` 时，agentKey 命中 tier 映射则优先用那个 profile |
| `internal/settings/settings.go` | 三个新键 |
| `web/src/components/quick-start-card.tsx` | 模型档位一行 |

#### 坑

1. **不要覆盖用户在任务上显式选的 profile** —— 优先级：任务级 `LLMProfileIDs` > tier 映射 > 全局激活。
2. 关键词表会过时，`internal/llmmodel/tier.go` 里留一行注释指向这里，改模型名只改这个文件。

#### 验收判据

1. 配了 3 个 profile（高/中/低），`PUT /api/llm/tier` 设好后建任务 → 活动流能看到 planner 用高、worker 用低（或回放页 token 对比体现）。
2. 任务显式指定 `llm_profile_ids` 时，tier 不生效。
3. 关键词未命中 → 落到 `mid`，不报错。
